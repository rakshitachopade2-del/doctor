# Application contract

All paths below start with `/api`. JSON errors use `{error: string}` and an appropriate HTTP status. List endpoints return arrays unless an object shape is stated. Calendar dates use `YYYY-MM-DD`; schedule times use `HH:mm` in `Asia/Kolkata`. Event timestamps and session expiry values are ISO timestamps.

Requests that change state use JSON. Except for login, registration, recovery-token redemption and the separate MFA challenge flow, they require an authenticated session and the session’s `X-CSRF-Token` header. MFA verification/cancellation instead requires its short-lived challenge cookie and `X-MFA-CSRF-Token`. Browser-origin checks also apply. The session cookie is HTTP-only, uses `SameSite=Lax`, and is secure in production. Roles, account status and patient ownership are enforced by the server, not only the interface.

Core models are in `shared/types.ts`; scheduling, waitlist, identity, operations, clinical workflows, PDF reports, follow-up reviews/assignments and activity models are in `shared/scheduling.ts`, `shared/waitlist.ts`, `shared/identity.ts`, `shared/operations.ts`, `shared/clinical.ts`, `shared/documents.ts`, `shared/follow-up.ts` and `shared/activity.ts`.

Demo accounts use `DemoClinic2026!` with `doctor@derma.demo`, `reception@derma.demo`, `patient@derma.demo` and `admin@derma.demo`. Demo records are synthetic and cannot be used as a production database.

## Authentication and account lifecycle

- `GET /session` → `Session` (`user`, optional `csrfToken`, `demoMode`). Account data includes normalized `active` and `mustChangePassword` flags.
- `POST /auth/login {email,password}` → `Session` with `200`, or `MfaChallenge` with `202` when a second factor is enrolled. A challenge grants no signed-in session. Inactive accounts cannot sign in. A temporary-password account receives a restricted session until its password is changed.
- `POST /auth/register {name,email,password,phone,dob,gender}` → `Session`; creates a new patient and patient account. Email and date of birth are required.
- `POST /auth/logout` → `{ok:true}`; ends the current session.
- `POST /auth/password {currentPassword,newPassword}` → `{ok:true}`. Passwords require 12–128 characters, and the new password must differ from the current one. Clears the initial-password requirement, ends other sessions and invalidates outstanding recovery grants.
- `GET /auth/sessions` → `AccountSession[]` for the current account: opaque `id`, `createdAt`, `expiresAt`, `current`, and coarse browser `label`. Sessions expire twelve hours after creation.
- `POST /auth/sessions/revoke-others {}` → `{ok:true,revoked:number}`.
- `DELETE /auth/sessions/:id {}` → `{ok:true}`; only the account’s own sessions can be revoked. Revoking the current session also clears its cookie.
- `GET /accounts?search=&role=` → `ManagedAccount[]` (administrator). Search matches name/email; role is one of `admin`, `doctor`, `receptionist`, `patient`.
- `PATCH /accounts/:id {name?,role?,doctorId?:string|null,active?}` → `ManagedAccount` (administrator). Role, linked-profile or active-status changes revoke all target sessions and recovery grants. A doctor role requires a valid doctor profile; a receptionist cannot have one. Patient/staff conversion and patient relinking are rejected. Self-suspension is rejected, and removing the final active administrator returns `409`.
- `POST /accounts/:id/recovery {identityVerified:true}` → `RecoveryGrant` (`token`, `expiresAt`) (administrator, active target account only). The 64-character token is returned once, stored only as a digest, expires after thirty minutes and replaces any earlier grant for that account. Issuing a grant does not itself end existing sessions.
- `POST /auth/recover {token,password}` → `{ok:true}` (no session or CSRF token required). Redeems a valid grant once, changes the password, clears the initial-password requirement and ends all target-account sessions and recovery grants. It does not sign the account in. Invalid, expired and inactive-account grants use a generic error.

Recovery links are shared manually after the clinic verifies identity. The frontend reads the token from `/recover#token=...` and removes it from the address bar. The server does not send recovery email or SMS. Authentication, password changes and recovery actions are rate-limited.

Authentication limits use persistent, independent fifteen-minute windows. Login allows twenty requests per network address and ten failed passwords per normalized email; the eleventh password attempt is blocked even if correct. Registration, password changes and recovery-link issuance allow ten network requests per operation; recovery redemption allows twenty. Schema-invalid JSON requests that reach the route consume the network budget only; malformed JSON and requests rejected by earlier origin, content-type or session guards never reach these counters. Unknown, inactive and wrong-password accounts return the same `401` response and consume the same identifier failure budget. A successful password step clears its identifier failures only after current credentials are revalidated and the session or MFA challenge commits. It does not reset network limits or the separate MFA proof budget.

An exhausted network or password-failure budget returns `429 {error:string}` with an integer `Retry-After` header giving the remaining seconds. Rejected attempts do not extend the fixed window. Limits survive process restart and are shared by application instances using the same database. Forwarded addresses are used only with the configured trusted proxy.

Failed-password audit entries are bounded to the first and tenth failure per identifier window, plus the first rejection per exhausted budget. They use record type `auth-security`, actor `Unauthenticated`, and keyed digests rather than raw submitted email/network addresses. Passwords, tokens and request bodies are excluded. Registration commits patient/account creation, audit and session atomically; logout commits current-session revocation, pending MFA setup removal and `signed out` audit atomically. Cookies change only after those commits. Network admission is a separate transaction: an admitted request remains counted if later validation, audit or session writes fail, while the associated identifier/audit or account/session changes roll back together.

Restricted temporary-password sessions can change their password, sign out or manage their own sessions. They cannot read private clinic/patient data or perform workspace operations. Public discovery/settings/availability/knowledge reads remain available.

## Optional authenticator MFA

Types are in `shared/mfa.ts`. MFA requires a configured `MFA_ENCRYPTION_KEY` (64 hexadecimal characters); accounts remain unenrolled until explicit setup. Ordinary password login remains available for unenrolled accounts. All MFA responses are private/no-store, and routes reject unknown query/body fields. Own-account management is unavailable to temporary-password sessions until password rotation completes.

- `GET /auth/mfa` → `MfaStatus`: key availability, enabled state/date, remaining recovery-code count, revision, pending metadata and the latest 100 sanitized security events. No secrets or proof values are returned.
- `POST /auth/mfa/enrollment/prepare {currentPassword,expectedRevision,requestId}` → `MfaPreparation`. Verifies the password and stages a secret, authenticator URI and ten recovery codes for ten minutes. A preparation does not activate MFA. New preparation replaces prior pending material.
- `POST /auth/mfa/enrollment/confirm {pendingId,code,savedRecoveryCodes:true,expectedRevision,requestId}` → `MfaMutation`. Requires the staged authenticator's code and explicit saved-code acknowledgment. Activates the factor and recovery hashes, consumes the accepted time step and destroys pending secret material.
- `POST /auth/mfa/recovery-codes/prepare {currentPassword,proof,expectedRevision,requestId}` → `MfaPreparation`. Password and existing factor are required. Stages replacement codes while the previous set remains active, except any old recovery code consumed as proof. The confirmation uses the returned `status.revision`, which can differ from the preparation's original source revision.
- `POST /auth/mfa/recovery-codes/confirm {pendingId,savedRecoveryCodes:true,expectedRevision,requestId}` → `MfaMutation`. Checks the current revision and same session/security context before replacing the entire active recovery-code batch.
- `POST /auth/mfa/disable {currentPassword,proof,expectedRevision,requestId}` → `MfaMutation`. Verifies both factors and removes enrolled material. It does not change the password.

`proof` is `{method:'totp'|'recovery-code',code:string}`. Canonical request UUIDs bind actor, session, operation and an HMAC of the normalized payload. Exact completed-command replay returns the original sanitized event plus current safe status before stale/consumed-proof checks. Preparation replay additionally verifies the current password and only returns the same encrypted pending material while unexpired and unsuperseded. Changed command intent is `409`; stale revision is `409`; expired/superseded preparation is `410`. All successful security mutations and audit records commit atomically. Factor changes end other sessions and challenges; the currently proven session remains valid.

For enrolled accounts, correct password login returns a five-minute `MfaChallenge` containing `mfaRequired:true`, intended `accountId`, a separate CSRF token and expiry. Its random token is in an HTTP-only `derma_mfa_challenge` cookie, scoped to `/api/auth/mfa`; only its digest is stored. The presented prior full session is ended/cleared.

- `GET /auth/mfa/challenge` restores valid challenge metadata without authenticating the account.
- `POST /auth/mfa/verify {proof}` with challenge cookie and `X-MFA-CSRF-Token` → full `Session` only after a valid one-use proof. Session creation, challenge/code consumption and audit commit together; the full session cookie is emitted after commit.
- `POST /auth/mfa/challenge/cancel {}` with the challenge credentials → `{ok:true}` and clears the challenge.

Invalid/expired challenges return `401`; invalid proof returns `400`; exhausted attempts return `429`. A durable account budget limits failures to ten per fifteen-minute window across challenges and restarts. Accepted authenticator steps and recovery codes cannot be reused. Lost verification responses can be reconciled through `/session` only when its user matches the challenge's intended account; otherwise restart password authentication with a fresh proof. Challenge metadata must never replace full-session state or CSRF credentials.

Password change, recovery and account access changes invalidate pending MFA preparations/challenges. Password recovery preserves enrolled MFA and does not log the user in. There is no administrator HTTP reset endpoint. The local operator reset requires explicit identity-verification acknowledgment and a reason, removes factors, ends sessions and requires password rotation. Key and reset procedures are documented in `DEPLOYMENT.md`.

## Administration and public configuration

- `GET /users` → normalized account data (administrator; retained for staff and portal setup).
- `POST /users {name,email,password,role,doctorId?}` → `User` (administrator). Roles are `doctor`, `receptionist` or `admin`; doctors require a profile. New accounts have `active:true` and `mustChangePassword:true`.
- `GET /doctors` → `Doctor[]` (public). Each profile includes its current `appointmentDurationMinutes`.
- `POST /doctors`, `PATCH /doctors/:id` → `Doctor` (administrator; full profile: name, title, qualifications, specialties, experience, fee, bio, languages, optional color).
- `GET /settings` → `ClinicSettings` (public fields only).
- `PATCH /settings` → `ClinicSettings` (administrator; partial clinic fields). Timezone remains `Asia/Kolkata`; module settings cover `intake`, `images` and `followUp`.
- `GET /audit` → `AuditEntry[]` (administrator).
- `GET /health` → `{status:'ok'}`.

Disabling a module pauses its new activity. Existing records remain readable within the usual permissions. The clinic’s public `hours` string is descriptive; bookable hours are configured by scheduling endpoints.

## Availability and appointments

- `GET /scheduling` → `SchedulingData` (`schedules`, `closures`, `timezone`, `bookingWindowDays`) (staff). Includes an effective schedule for every doctor, including defaults.
- `GET /schedules/:doctorId` → `DoctorSchedule` (staff).
- `PUT /schedules/:doctorId {durationMinutes,windows}` → `DoctorSchedule` (administrator, or doctor managing their own profile). `durationMinutes` is `15 | 20 | 30 | 45 | 60`. Each window is `{day,start,end,mode}`: day `0` is Sunday through `6` Saturday, and mode is `in-person | online | both`. Empty windows close all weekly availability. Sessions must not overlap on a day, even across different modes, and each must fit at least one appointment. Saved windows are sorted by day/start.
- `POST /schedule-closures {doctorId,startDate,endDate,startTime,endTime,reason}` → `ScheduleClosure` (administrator, or doctor for their own profile). `doctorId:null` applies to the entire clinic and requires an administrator. Both times `null` mean all day; otherwise the same start/end interval applies on each included date. End date must not precede start date or today. The end time must be later on the same day; overnight intervals are not supported.
- `DELETE /schedule-closures/:id {}` → `{ok:true}` (administrator or the closure’s owning doctor).
- `GET /slots?doctorId=&date=&mode=&excludeAppointmentId=` → available start-time strings. Public reads omit `excludeAppointmentId`; supplying it requires access to that appointment and excludes its current reservation when rescheduling. Optional mode is `in-person` or `online`. Signed-in patients’ own overlapping appointments are also filtered.
- `GET /appointments?date=&doctorId=` → `Appointment[]` (staff or owning patient).
- `POST /appointments {patientId?,doctorId,date,time,mode,reason,waitlistId?,patientConfirmed?}` → `Appointment` (staff or owning patient). The server assigns the selected doctor’s current appointment duration. Linking `waitlistId` requires `patientConfirmed:true` and the matching patient, doctor, consultation mode and requested date window; normal slot checks still apply.
- `PATCH /appointments/:id {status?,date?,time?,doctorId?,mode?}` → `Appointment`. Rescheduling is allowed only while scheduled and cannot be combined with a non-scheduled status change. Patients may reschedule or cancel their own scheduled appointments. Clinic states follow the allowed transition graph; only clinicians can start or complete a consultation.
- `GET /appointments/:id/calendar` → authorized `.ics` download, using the appointment’s recorded duration and IST start time.

Defaults are Monday–Saturday, 09:00–18:00, thirty-minute appointments and both consultation modes. Configured schedules may use other weekdays and multiple daily sessions. The booking horizon is currently 180 days; past times are never offered. The server checks full interval overlap for doctor and patient inside a transaction, including older appointments of a different length.

A schedule change or closure that invalidates existing future bookings returns `409`, leaving both availability and appointments unchanged. Existing bookings must be rescheduled or cancelled first. Changing a schedule alone preserves their duration. Explicit rescheduling adopts the selected doctor's current duration for ordinary visits; `durationPolicy:'custom'` preserves saved custom minutes. Legacy appointments without `durationMinutes` are treated as thirty minutes, and omitted policy means `schedule`. Removing a closure restores the hours allowed by the weekly schedule.

Temporary-password sessions receive anonymous slot availability: their patient-specific busy periods are not applied, and `excludeAppointmentId` is rejected until password rotation.

## Custom visit durations

Staff may explicitly choose 15–240 minutes in five-minute increments. Custom start times use a five-minute grid relative to each weekly session's start. Ordinary consultations use the doctor's default duration and cadence. Both policies require the whole interval to fit one matching session and avoid doctor, patient and closure conflicts within the existing 180-day horizon. Retained resources use the same effective interval.

- `GET /visit-duration/slots?doctorId=&patientId=&date=&mode=&durationPolicy=&durationMinutes=&excludeAppointmentId=` is staff-only and returns start-time strings. Policy is `custom|schedule`; custom requires valid minutes and schedule omits them. Exclusion requires the same patient and filters retained resource conflicts. Parameters are strict, including duplicate rejection. Public `/slots` does not accept duration overrides; authorized reschedules derive policy and length from the stored appointment.
- `POST /visit-duration/bookings {patientId,doctorId,date,time,mode,reason,durationMinutes,requestId}` creates a staff-booked custom visit. It returns `VisitDurationMutation {appointment,event}` with 201; exact replay returns 200. The appointment reason follows normal booking visibility, while the separate event is staff-only. This path does not convert waitlist requests or allocate resources automatically.
- `GET /appointments/:id/duration` is staff-only and returns `VisitDurationContext {appointment,revision,scheduleDurationMinutes,currentDoctorFee,currentDoctorName,canChange,history}`. History contains immutable custom-booking and explicit duration-change events; it is not a complete history of ordinary appointment edits.
- `POST /appointments/:id/duration {durationPolicy,durationMinutes?,date,time,reason,expectedRevision,requestId}` changes a future scheduled visit and returns `VisitDurationMutation` with 200. Custom requires minutes; schedule uses the current doctor default. Date/time are required and may move together with the duration. Patient, doctor and mode remain fixed in this operation. A no-op, past source visit or non-scheduled source is rejected. The internal reason is required (1–1,000 characters) and never enters patient summaries or notifications.

The revision covers the current appointment and current doctor's schedule, fee and name. A changed source returns 409 and requires refreshed-context review. Canonical lowercase UUIDs bind actor, operation, target and normalized payload, including the revision. Exact retry occurs after authorization but before source/state/slot checks, returning the current appointment alongside its original immutable event. Reusing an ID with different intent returns 409. Original events and request receipts reject updates/deletion. Appointment changes, resource moves/resizing, evidence, audit and in-app notification commit together; any failure rolls them back.

A duration-only or policy-only change preserves the booked fee/name. An actual date/time move adopts the current doctor fee/name under the existing reschedule rule. Generic staff/patient PATCH reschedules preserve custom minutes and refresh ordinary default lengths; clients cannot supply duration fields through ordinary POST/PATCH. Status-only changes preserve duration, policy and fee. Calendar exports and patient summaries use actual recorded minutes. This feature does not rewrite procedure links, agreements, completions or invoices.

## Appointment waitlist

- `GET /waitlist?status=&doctorId=` → `WaitlistEntry[]` (staff or owning patient). Optional status is `waiting | booked | cancelled | expired`. Staff can see all clinic requests and operational `patientPhone`; patients receive only their own requests without that phone field.
- `POST /waitlist {patientId?,doctorId,mode,startDate,endDate,reason}` → `WaitlistEntry` with `201`. Staff supply a patient; patient accounts use their own linkage and cannot substitute another patient. Mode is `in-person | online`; reason requires 1–300 characters. The inclusive ordered date window must be within today through 180 days ahead. A second waiting request for the same patient, doctor and mode returns `409`, even if its date window differs.
- `POST /waitlist/:id/cancel {reason?}` → `WaitlistEntry` (staff or owning patient). The optional reason has a 300-character limit. Cancelling a waiting request preserves its original record. Repeating cancellation returns the existing result and retains the first reason; booked or expired requests return `409`.

Each entry contains patient/doctor IDs and names, mode, date window, reason, creation time, derived status, nullable `appointmentId`, `closedAt` and `cancellationReason`. Expiry is derived when the end date precedes the current clinic date; no background job or expiry notification is required. Joining does not reserve a slot, prioritize urgency, offer an appointment automatically or send external messages.

Booking uses the ordinary `POST /appointments` endpoint with the request ID and explicit patient confirmation. The appointment, terminal waitlist record, audit and in-app notification commit atomically. An already booked, cancelled or expired request cannot be booked again. Later rescheduling or cancelling the appointment preserves the request's booked history; a separate new request can be created. Staff coordinate patient contact separately, and patients can choose an available slot from their own request.

## Patient records and care

- `GET /dashboard` → `Dashboard` (staff; receptionist responses exclude clinical follow-up details).
- `GET /patients?search=` → `Patient[]` (staff; receptionist responses contain demographics only).
- `POST /patients {name,email,phone,dob,gender,allergies}` → `Patient` (staff). Walk-in records may use empty email/date of birth; reception cannot enter clinical allergies.
- `GET /patients/:id` → `PatientRecord` (clinician or owning patient; reception denied). Internal encounters are omitted from patient responses.
- `POST /patients/:id/portal-account {email,password,identityVerified:true}` → `User` (administrator). Requires an unlinked patient record and unused email; creates an active account requiring an initial-password change. Existing accounts cannot be relinked through this endpoint.
- `POST /intakes {patientId?,concern,location,duration,symptoms,triggers,previousTreatment,medications,allergies,goals,consent:true}` → `Intake` (owning patient or clinician; intake module must be enabled).
- `POST /encounters {patientId,appointmentId?,history,examination,assessment,investigations,plan}` → `Encounter` (clinician with a linked doctor profile). Notes are immutable; a linked appointment must belong to the same patient.
- `GET /care-plans` → `CarePlan[]` (clinician or owning patient), including effective follow-up status/date, revision and latest review as described below.
- `POST /care-plans {patientId,title,instructions,expectations,warnings,cost,startDate,endDate,followUpDate,medications}` → `CarePlan` (clinician with a linked doctor profile). Each medication has name, instructions, schedule, duration and warnings.
- `PATCH /care-plans/:id {status,expectedRevision?}` → hydrated `CarePlan` (clinician with a linked doctor profile); status is `active` or `completed`. A change appends a factual `source:'status-change'` event and patient notification. It does not clear unreviewed check-ins or record new clinical advice. Repeating the current status creates no additional event. An optional stale revision returns `409`.
- `POST /check-ins {carePlanId,date,adherence,feeling,note}` → `CheckIn` (owning patient, active plan, follow-up module enabled). One per plan/day, updated on repeat; dates must be within the plan and not in the future. Adherence is `taken | partial | missed`; feeling is `better | same | worse`.
- `POST /images {patientId?,caption,category,consent:true,dataUrl}` → `ClinicalImage` (owning patient or clinician; image module enabled). Category is `clinical` or `report`. Private JPEG/PNG/WebP images are limited to 5 MB and checked for a matching file signature.
- `GET /images/:id/file` → private image bytes with ownership checks.
- `GET /messages?patientId=` → `Message[]` (clinician or owning patient).
- `POST /messages {patientId?,body}` → `Message` (clinician or owning patient; follow-up module enabled). Messages have a 4,000-character limit and remain inside the platform.

## Follow-up review and worklist

- `GET /follow-up-worklist?scope=mine|all` → `FollowUpWorkItem[]` (doctor/administrator). Defaults to `mine` for doctors and `all` for administrators. Ownership starts with the original care-plan doctor and follows the latest assignment; `all` uses the existing clinic-wide clinical permissions. Includes active and completed plans, sorted by due status, unreviewed count, next review date and patient name. Each item contains `carePlan`, `patient`, `ownerDoctorId`, `ownerDoctorName`, `revision`, `latestReview`, `unreviewedCheckIns`, `unreviewedCount` and `due`.
- `GET /care-plans/:id/reviews` → newest-first `FollowUpReview[]` (clinician) or `PatientFollowUpReview[]` (owning patient). Reception is denied. Patient responses omit internal `assessment` and `checkInSnapshots`.
- `POST /care-plans/:id/reviews {expectedRevision,assessment,patientInstructions,disposition,nextReviewDate?}` → hydrated `CarePlan` with `201` (linked clinician; follow-up module enabled). Assessment and patient instructions are required, with an 8,000-character limit each. Disposition is `continue | visit-requested | complete`. Continuing or requesting a visit requires today's date or a future `nextReviewDate`; completion stores `null`. `expectedRevision` must match the current 64-character revision from the plan/worklist. A new review, assignment or new/edited check-in makes an earlier revision stale and returns `409` without saving.
- `GET /follow-up-owners` → `FollowUpOwner[]` (doctor/administrator): `doctorId`, `doctorName` and `activeAccounts`. Eligible profiles have at least one active linked doctor/administrator account; an account still requiring its initial password change counts as active.
- `GET /care-plans/:id/assignments` → newest-first `FollowUpAssignment[]` (doctor/administrator; patients and reception denied). Each event records the previous/new doctor IDs and names, reason, assigning account ID/name and creation time.
- `POST /care-plans/:id/assignment {doctorId,reason,expectedRevision}` → hydrated `CarePlan` with `201`. Administrators, including those without a doctor profile, can reassign; a doctor must be the current follow-up owner. The handover reason requires 1–8,000 characters and the current 64-character revision is mandatory. An ineligible target returns `400`; the current owner as target or a stale revision returns `409`.

Assignment changes the worklist owner and routing for subsequent check-in notifications, preserving original plan/review authorship. Assignment history and reasons remain clinician-only; patient hydration includes only an opaque changed revision. Reassignment records an immutable event, audit and generic new-owner notification together. It does not clear unreviewed reports or revise treatment. Operational reassignment remains available when the follow-up module is paused.

Hydrated care plans in plan lists, patient records and dashboard follow-ups include `effectiveStatus`, `effectiveFollowUpDate`, `followUpRevision` and `latestReview`. Their original `startDate`, `endDate` and `followUpDate` remain unchanged. A plan is due when active and its effective review date is today or earlier. The latest event determines active/completed status and the next review date; completed plans have no effective review date. Patient-facing hydration applies the same internal-field filtering as review history.

Each immutable `FollowUpReview` records its ID, plan, linked doctor/name, `source` (`clinical-review | status-change`), assessment, patient instructions, disposition, next review date, timestamp and full check-in snapshots. Each snapshot carries the check-in `id`, `updatedAt`, SHA-256 `contentHash` and original `snapshot`. The snapshot timestamp reflects the check-in's latest stored submission time, including a same-day replacement. The server captures these fields; clients cannot provide or replace them. Current versions not captured by the latest clinical review remain unreviewed. Editing a previously reviewed check-in reopens that work while preserving the exact evidence previously reviewed.

Completing a plan stops check-ins. Continuing follow-up does not extend the original treatment dates or medication duration; `visit-requested` does not book an appointment. A status-only change can reopen a plan but does not count as clinical review. Existing history and the status-only endpoint remain available when the follow-up module is disabled. Check-ins describe patient reports; review queues and dispositions do not diagnose, triage urgency or generate treatment advice.

## Follow-up escalation

Types are in `shared/follow-up-escalation.ts`. All routes reject unknown input/query fields, require a normal authorized session, and return `Cache-Control: no-store`.

- `GET /follow-up-escalation-policy` → `EscalationPolicyContext` (doctor/administrator): current policy/revision, newest-first policy history, follow-up module state and actual local worker state. Default policy: `{enabled:false,ownerAfterDays:3,clinicAfterDays:7}`; initial history is empty.
- `POST /follow-up-escalation-policy {enabled,ownerAfterDays,clinicAfterDays,reason,expectedRevision,requestId}` → `EscalationPolicyMutation` with `200` (administrator). Owner threshold is an integer 1–30; clinic threshold must exceed it and be at most 90. Reason is trimmed, 1–1,000 characters. A no-op is `400`; a stale revision is `409`. A canonical UUID is bound to the actor and normalized command. Exact replay returns the original change with the current context, including after later policy changes.
- `GET /follow-up-escalations/preview` → `EscalationPreview` (administrator). Contains clinic date, policy/revisions, `ready | disabled | paused` status, full ready/unroutable/already-notified counts and up to 200 ready candidates, oldest review date/plan ID first. Candidates preserve plan/patient/owner identity, source review/assignment IDs, episode, overdue days, stage, routing and exact recipient account snapshots. Disabled/paused policies can show hypothetical candidates but cannot create notices. Reading never sends.
- `POST /follow-up-escalations/run {expectedPreviewRevision,expectedPolicyRevision,requestId}` → `EscalationRun` with `200` (administrator). Recomputes the preview transactionally and rejects stale source/recipient/date/policy/module state with `409`. Disabled or paused policies also return `409`. Actor-bound exact replay returns the original run before checking newer source state. A new zero-notice check can return a receipt with zero counts. Events, exact-recipient activity, receipt and audit commit together.
- `GET /care-plans/:id/escalations` → `EscalationHistory` (doctor/administrator). Exact plan identity, current operational state and newest-first immutable events across review episodes, including completed plans. Patient/reception access is denied. Reading history does not resolve the plan or mark activity read.

Overdue days are Asia/Kolkata calendar days after the effective review date; the date itself is zero. Completed plans and plans without a reached threshold are ineligible. An episode binds plan ID, latest review/status-change ID and effective review date. A recorded clinic-stage notice suppresses future owner-stage notices for that episode; an owner notice can be followed by a later clinic notice. A plan already at the clinic threshold receives only that stage. Check-ins, assignments and policy edits do not reset dedupe.

Owner routing targets active linked clinician accounts for the current owner, falling back to eligible clinic clinicians when unavailable. Clinic routing targets all eligible clinical accounts. Inactive accounts, accounts still requiring their initial password change and missing/invalid clinician links are excluded. No eligible recipients means no event or consumed dedupe key, allowing a later retry. Recorded recipient snapshots do not imply read state or external delivery. Only the clinical worklist receives operational `escalation` state; these fields never enter patient care-plan hydration or summaries, and notices/policy edits do not change clinical review revisions.

The server runner uses the same service at startup and every 900 seconds unless `FOLLOW_UP_ESCALATION_AUTO=false`. Automatic receipts use `source:'automatic'`, null request/actor IDs and `createdByName:'Follow-up scheduler'`; no-notice polls only update bounded heartbeat metadata. API app construction alone does not start it. Events use the existing `follow-up` activity kind and an exact-plan `/clinic/follow-ups?escalation=...` link.

## In-app activity

- `GET /activity?unread=true|false&limit=&cursor=` → `ActivityFeed` (`items`, `unreadCount`, `nextCursor`). Limit defaults to 30, with a range of 1–100. `unread=true` filters the page; `false` or omission includes read and unread items. The count covers all currently unread items for the recipient, not just the page. Items are newest first. Pass the previous `nextCursor` to load older items; a cursor outside the account's permitted feed returns `400`.
- `POST /activity/:id/read {}` → `ActivityItem`. Only the recipient can mark an item read; an inaccessible item returns `404`. Repeated reads preserve the initial `readAt`.
- `POST /activity/read-all {throughId}` → `{markedRead:number}`. Marks all unread items for the recipient at or before the supplied feed item, including older pages not yet loaded. Use the newest item from the displayed snapshot. Items arriving after that snapshot stay unread; an inaccessible snapshot ID returns `404`.

An `ActivityItem` has `id`, `kind`, `title`, `detail`, `href`, `createdAt` and nullable `readAt`. Kinds are `appointment`, `care-plan`, `message`, `check-in`, `investigation`, `procedure`, `follow-up`, `waitlist`, `billing` and `image-annotation`. Waitlist creation/cancellation/booking, follow-up handover, invoice creation, recorded payments and billing corrections generate supported in-app events. A waitlist booking sends one request-specific booking notification, without duplicating the ordinary appointment-created notification. Event contents are immutable; read state is separate. Listing a feed never marks it read, and reading a notification does not mark clinical information reviewed or complete a task.

Feeds are account-specific. Patients see only their own patient notifications; doctors and administrators see their own clinical notifications; reception receives an empty feed. Current account permissions still apply after role changes. Clinical events with an assigned doctor route to active linked accounts for that doctor, falling back to the active clinical team only when no owner account is active. The author is excluded after recipient selection. Patient messages without a specific owner notify the active clinical team. No notification exposes internal assessments, unpublished interpretations or private message text.

Notifications are recorded with the source event in one transaction and deduplicated by recipient/event key. Events notify accounts active at that moment; creating or reactivating an account does not backfill earlier events. These are in-app updates only: no email, SMS, push delivery or emergency monitoring is configured. Enabled follow-up escalation policies can create scheduled in-app notices for overdue review dates.

## Image annotations and patient-facing summaries

- `GET /images/:id/annotations` → `ImageAnnotationHistory` (`imageId`, `revision`, `versions`). Clinical staff receive all revisions with a SHA-256 optimistic revision token. Owning patients receive published revisions only and `revision:null`; no private revision IDs, notes or counts are exposed. Reception is denied. Versions are newest first.
- `POST /images/:id/annotations {expectedRevision,note,markers}` → updated history with `201` (linked clinician). A nonempty note or at least one marker is required. Notes allow up to 4,000 characters; at most 50 markers are accepted. New versions are always private, retain clinical authorship/date and the original image fingerprint, and never change image bytes. The current revision is checked transactionally; stale saves return `409`.
- `POST /images/:id/annotations/:versionId/publish {expectedRevision,patientSharingConfirmed:true}` → updated history (linked clinician). Newly sharing requires the current revision and latest saved version. Repeating a previously completed publication preserves its original timestamp and notification. Explicit publication, audit and a generic patient activity entry save in one transaction. There is no edit/delete/unpublish endpoint.

Each marker has a unique UUID `id`, a color from `red | amber | green | blue | purple | white`, and an optional label up to 200 characters. Rectangle/ellipse markers have `type`, `x`, `y`, `width`, `height`; arrow markers have `type:'arrow'`, `x1`, `y1`, `x2`, `y2`. All coordinates are image-relative values from 0 to 1, rounded to six decimal places. Box dimensions must stay positive and entirely within the image. Arrow endpoints must differ. Arbitrary geometry fields, SVG markup, colors and client-authored provenance are rejected. Coordinates describe position, not physical measurements or automated clinical interpretation.

The image module must be enabled to save or publish. Existing history remains readable while paused. Original image rows, annotation versions and publication events are immutable. New image uploads record authenticated uploader metadata, byte count and SHA-256; legacy uploads retain absent provenance rather than fabricated authorship. Upload plus audit is transactional.

- `GET /patients/:id/care-summary` → `CareSummary` (`schemaVersion:1`, `audience:'patient'`, `generatedAt`, `timezone:'Asia/Kolkata'`, `revision`, clinic contact, patient, appointments, intakes, care plans with patient-facing review history, check-ins, investigations, procedures, image metadata/published annotations, PDF metadata, invoices and safe `invoiceHistories`). Patients may access only their own summary; clinical staff may access the clinic's patients. Reception is denied. Both eligible role groups receive the same patient-facing projection.
- `GET /patients/:id/care-summary/download?revision=` → private JSON attachment. The required 64-character revision must match the current patient-visible content; stale requests return `409` and require a refresh. The export can have a later generation timestamp but must have the same content revision. Filename uses an opaque identifier rather than the patient's name. Responses use no-store and nosniff headers, with authorization and audit on every request.

Summaries exclude internal encounters/amendments, private messages, clinician follow-up assessments/report snapshots/assignment reasons, unpublished investigation interpretations, private image annotations and original file bytes. Attachment URLs remain private authenticated routes. Private drafts and operational handovers do not invalidate a summary unless patient-visible content actually changes. Original regimen dates and instructions remain distinct from later shared follow-up reviews. Printing keeps the displayed snapshot; this is a patient-facing summary rather than a complete internal clinical-record release.

## Private PDF reports

- `GET /documents?patientId=` → `PatientDocument[]` (doctor/administrator or owning patient; reception denied). Patient accounts default to their own record; clinical staff supply `patientId`.
- `POST /documents {patientId?,title,originalName,dataUrl,consent:true}` → `PatientDocument` with `201`. Accepts canonical base64 `application/pdf` data URLs, up to 5 MB decoded, inside the existing 7 MB JSON request limit. Title and original filename have a 200-character limit. Filenames must end in `.pdf` and contain no path separators or control characters. The server validates PDF header/end markers and records the authenticated uploader, byte count and SHA-256 fingerprint.
- `GET /documents/:id/file` → authorized PDF attachment. The server uses a generated download filename, `Content-Disposition: attachment`, `Content-Security-Policy: sandbox; default-src 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`.

`PatientDocument` contains `id`, `patientId`, `title`, `originalName`, `mimeType:'application/pdf'`, `sizeBytes`, `sha256`, `createdById`, `createdByName`, `createdByRole`, `createdAt`, `url` and `consent:true`. List responses contain metadata, not file bytes. Document metadata and original bytes are immutable; there is no edit/delete endpoint. PDFs use separate storage and routes from the raster image library.

These checks recognize a candidate PDF; they do not sanitize or malware-scan it. Original files are downloaded rather than embedded. The fingerprint identifies the uploaded bytes, not their issuing laboratory or medical accuracy. Upload agreement records private care use and does not authorize public publication.

## Investigations, procedure records and amendments

`GET /patients/:id/clinical-workflows` → `PatientClinicalWorkflows` with `investigations`, `procedures` and `amendments` arrays. Doctors and administrators may inspect the clinic's records; patients receive only their own. Reception is denied. Patient responses contain no internal encounter amendments and omit every unpublished investigation-review object. Top-level arrays are newest first; nested results, reviews and procedure agreements are chronological, so the last entry is the latest.

All clinical authorship below requires an account linked to a doctor profile, including administrators. An unlinked administrator can inspect authorized records but cannot create orders, clinical interpretations, amendments or procedure records. Names, identifiers, roles and timestamps are derived by the server.

### Investigation orders and review

- `POST /investigations {patientId,title,kind,reason,instructions,dueDate?}` → `Investigation` with `201` (linked clinician). Kind is `laboratory | pathology | imaging | other`. Reason and patient-facing instructions are required; optional due date may be `null` or today/a future date. The original order is immutable.
- `POST /investigations/:id/results {note?,documentIds?}` → updated `Investigation` with `201` (owning patient or linked clinician). Requires a note or at least one PDF-report ID. The 0–10 document IDs must be unique and belong to the same patient. Each submission is an immutable `InvestigationResult` with authenticated `submittedById`, name, role and timestamp. Notes and raw reports are patient-visible and remain distinct from clinician interpretation.
- `POST /investigations/:id/reviews {resultId,summary,followUp?,publishToPatient?,expectedRevision?,requestId?}` → updated `Investigation` with `201` (linked clinician). The selected result must be the latest submission; a stale selection returns `409`. Summary is required. Publication defaults to `false`; explicit `publishToPatient:true` shares the interpretation. Review text is immutable; subsequent reviews are additional entries.
- `POST /investigations/:id/reviews/:reviewId/publish {}` → updated `Investigation` (linked clinician). Explicitly shares an existing interpretation without changing its content. Repeating the publication preserves its original publication timestamp. New publication on a cancelled investigation returns `409`, while an already published review remains idempotently readable through this action.
- `POST /investigations/:id/cancel {reason}` → updated `Investigation` (linked clinician). Cancellation preserves history and prevents new results/reviews. A cancelled order or an investigation whose latest result is already reviewed returns `409`.

Investigation status is derived: `ordered` before a result, `result-received` when the latest submission has no review, `reviewed` after a clinician reviews that latest submission, or `cancelled`. A supplemental submission returns the order to `result-received` and retains earlier results and interpretations. A reviewed result may still have no patient-visible interpretation until explicit publication. The application does not classify a result as normal/abnormal or generate a diagnosis.

### Investigation worklist and responsibility

All endpoints here require an active doctor or administrator account. Patients and reception are denied. Queue reads remain available while optional modules are paused.

- `GET /investigation-worklist?scope=mine|all` → `InvestigationWorkItem[]`. Defaults to `mine` for doctors and `all` for administrators. Includes all statuses, original ordering identity, current patient display name, current owner and `ownerAvailable`, original requested date, latest result/review IDs and dates, `needsReview`, `awaitingPublication`, `pastRequestedDate` and current revision. It omits result/review free text and assignment reasons. A doctor may inspect all clinic work; ownership is not an access boundary.
- `GET /investigation-owners` → `{doctorId,doctorName,activeAccounts}[]`, containing only clinician profiles with at least one active linked doctor/administrator account.
- `GET /investigations/:id/review-context` → `InvestigationReviewContext`, extending the work item with the full clinical `investigation` and newest-first `assignments`. Reads are audited and do not change review or activity state.
- `POST /investigations/:id/assignment {doctorId,reason,expectedRevision,requestId}` → current review context, `201` for a new assignment and `200` for exact replay. Only the current responsible doctor or an administrator may create a handover. Destination must have an active linked clinical account. Reason is trimmed 1–1,000 characters; UUID and current 64-hex revision are required. Assigning the same owner or a cancelled investigation returns `409`.

Assignment events retain previous/new doctor identity, private reason, actual recording account and timestamp. Existing investigations default to the original ordering clinician without fabricated assignment events. Source order, requested date and clinical authorship remain unchanged. Patient workflows and care summaries receive no assignment records, internal reasons or revisions; private handovers do not invalidate a patient-visible summary revision.

For review creation, `expectedRevision` and UUID `requestId` must be supplied together or both omitted for legacy callers. Current application forms always provide both. The revision covers results, reviews, publications, cancellation and assignment history. Changed source state returns `409`; an exact actor-bound retry returns the current clinical investigation with `200` without another review, even if later source changes occurred. Legacy callers retain the existing latest-result check but have no full-context concurrency or command replay guarantee. Multiple intentional reviews of the latest result remain supported after loading current context.

Review and assignment commands share an actor/operation/investigation/payload-bound UUID namespace. Expected revision is excluded from replay intent; mismatched reuse conflicts. Assignment replay checks precede current-owner checks so an original owner can safely confirm a completed handover. Source event, command receipt, audit and any notification commit atomically. New-result activity routes to the current owner and links to the exact submitted result; if no linked owner account is active, eligible clinical accounts receive the event using the existing fallback rules. Free-text handover reasons never enter notifications.

`needsReview` means the latest result has no review and the order is not cancelled. `awaitingPublication` means the most recent review of the latest result remains private on an uncancelled order. `pastRequestedDate` applies only to orders without a result whose original due date is earlier than today in Asia/Kolkata. It is not a review deadline, clinical severity score or urgency classification.

### Consultation amendments

- `POST /encounters/:id/amendments {reason,text}` → `EncounterAmendment` with `201` (linked clinician). Both fields are required. The server derives the patient from the original encounter and records the amending doctor and timestamp. The original consultation note remains unchanged. Amendments are returned only in the clinician's workflow view and cannot be edited or deleted.

### Procedure catalogue

Types are in `shared/procedure-catalogue.ts`. Catalogue reads are private to doctors and administrators. Creating versions and publishing requires a linked clinician; archive/reactivation requires an administrator. Patients and reception cannot read catalogue content or history. No patient indication, appointment, decision or outcome is stored in a template.

- `GET /procedure-catalogue?search=&active=&publication=&page=&pageSize=` → `ProcedureCataloguePage`. Active is `true|false|all` (default `true`); publication is `all|published|unpublished` (default `all`). Search is a literal substring of latest/published titles, up to 300 characters. Page sizes are 10/25/50, default 25; pages clamp to the current result set. Publication and active filters are independent.
- `GET /procedure-catalogue/:id` → `ProcedureTemplateDetail`: current row, latest version, current published version and its publication event (or null), latest 25 lifecycle events and total history count.
- `GET /procedure-catalogue/:id/versions?page=&pageSize=` → `ProcedureTemplateVersionPage`, newest version first.
- `GET /procedure-catalogue/:id/history?page=&pageSize=` → paginated immutable lifecycle events, newest first.
- `POST /procedure-catalogue {fields,reason,requestId}` → `ProcedureTemplateMutation {detail,event,version}`, 201 on creation or 200 on exact replay. Creates an active unpublished template with version 1.
- `POST /procedure-catalogue/:id/versions {fields,reason,expectedRevision,requestId}` → mutation. Creates a new immutable draft; current publication remains usable. Identical latest content is rejected.
- `POST /procedure-catalogue/:id/publish {versionId,reviewed:true,reason,expectedRevision,requestId}` → mutation. Explicitly publishes the exact latest version. Archived templates and superseded versions are rejected. An author may review their own content; this is not an independent approval process.
- `POST /procedure-catalogue/:id/availability {active,reason,expectedRevision,requestId}` → mutation. Archives or reactivates without removing content or existing patient plans. Reactivation restores the retained publication.

Fields are `title`, `benefits`, `risks`, `alternatives`, `aftercare`, and descriptive `estimatedCost`. Title is required up to 300 characters; discussion fields are required up to 8,000; cost text may be empty and is limited to 300. Reasons are required up to 1,000 characters. Reads and commands reject extra query/body fields. UUIDs are canonicalized; commands bind the account, target, operation and complete normalized input. A changed request under the same UUID or stale revision returns 409. Replay returns the original event and its immutable version (null for availability changes), with current detail, before state/no-op checks. Source, evidence, receipt and audit commit together.

`revision` changes on every lifecycle event. `selectionRevision` changes on publication or availability changes, including archive/reactivate cycles, but not when saving a draft. Private catalogue changes do not notify patients or modify care-summary content.

### Procedure discussion and completion

- `POST /procedures {patientId,appointmentId?,title,indication,benefits,risks,alternatives,aftercare,estimatedCost?,requestId?,templateSelection?,reviewedForPatient?}` (linked clinician). Legacy manual requests without a UUID return `ProcedureRecord` with 201. UUID requests return `ProcedureCreateMutation {procedure,receipt}`, 201 initially or 200 on exact replay. Discussion fields are required, and estimated cost is descriptive text. An optional linked appointment must belong to the same patient and must not be cancelled or marked as a no-show. A procedure plan is immutable; create a new plan if its explanation changes.
- `POST /procedures/:id/agreements {decision,method,note?,patientDecisionConfirmed?}` → updated `ProcedureRecord` with `201`. Decision is `agreed | declined`. An owning patient uses `method:'portal'`. A linked clinician may record an `in-person` or `phone` decision only with a nonempty discussion note and `patientDecisionConfirmed:true`; clinicians cannot impersonate a portal acknowledgement. Each event retains the actual recording account, role, method and timestamp.
- `POST /procedures/:id/complete {outcome,aftercare}` → updated `ProcedureRecord` (linked clinician). The latest recorded decision must be `agreed`. Completion records the performing doctor and server timestamp and requires outcome and aftercare. The effective appointment is resolved inside the transaction; it must exist, not be cancelled/no-show, and have started. New completion records include its safe `appointment` snapshot, or `null` when unlinked; legacy completions are not backfilled.
- `POST /procedures/:id/cancel {reason}` → updated `ProcedureRecord` (linked clinician).

Template selection is `{templateId,versionId,expectedSelectionRevision}` and requires a request UUID and `reviewedForPatient:true`. All final fields remain explicit, including the patient-specific indication. The server checks the active current publication and selection token in the plan transaction, then derives safe immutable `templateSource` attribution and changed-field names. Own-patient records and summaries include that attribution, never internal catalogue reasons, tokens, receipts or unpublished content. Later publication/archive does not change the saved plan. Exact actor-bound retries return the original receipt and current view of the same plan before later source/appointment eligibility checks; changed payload or actor under the UUID is rejected. Receipt, plan, audit and patient notification commit together.

A procedure starts as `planned`; `completed` and `cancelled` are terminal. Patient decisions can change while planned, and all earlier decisions remain visible. Agreement checks and completion/cancellation run transactionally. Completing or cancelling a procedure neither changes its appointment nor creates a billing charge. No separate procedure time slot is reserved.

### Scheduling existing procedure plans

These endpoints allow administrator, doctor and receptionist accounts. Patients are denied private scheduling reads and writes. Operational projections omit clinical discussion, agreement notes, outcomes, appointment reasons, fees and patient contacts.

- `GET /procedure-scheduling?search=&status=&booking=&page=&pageSize=` → `ProcedureSchedulePage`. Defaults: empty search, `status:planned`, `booking:all`, page 1, page size 25. Status is `planned|completed|cancelled|all`; booking is `unlinked|linked|attention|all`. Literal search matches patient name or procedure title, up to 300 characters. Page sizes are 10/25/50; out-of-range pages clamp. Rows sort by original creation date and ID descending. Filtering, counting and pagination happen in SQLite before row JSON decoding, in one coherent transaction.
- `GET /procedures/:id/scheduling` → `ProcedureScheduleContext {procedure,revision,history}`. The row contains original and effective appointment IDs, a safe current appointment snapshot, operational status, `canChange` and `blockedReason`. Immutable link events are newest first. The revision covers procedure identity/status, original/effective links, the current visit snapshot and latest link event.
- `GET /procedures/:id/scheduling/candidates?from=&to=&page=&pageSize=` → `ProcedureCandidatePage`. Returns same-patient future scheduled visits, excluding the current effective visit, with a revision of each safe snapshot. Dates default to today through 180 days ahead; explicit ranges must stay within that horizon. Page sizes are 10/25/50, with stable date/time/ID ordering and clamped pages.
- `POST /procedures/:id/scheduling {appointmentId,expectedAppointmentRevision,expectedRevision,requestId,reason,removeConfirmed?}` → `ProcedureScheduleMutation {context,event}` with 200. Attaching/replacing requires a target ID and its revision. Removal requires null ID/revision and `removeConfirmed:true`; that flag is rejected for a nonnull target. Reasons are trimmed, required and limited to 1,000 characters. Extra/duplicate query fields and extra command fields are rejected.

Only planned procedures can change links. A current missing/cancelled/no-show visit, future scheduled visit, or no link is eligible; a visit already checked in, in consultation, completed or past its scheduled start is read-only. Targets must be future scheduled visits for the same patient. Different clinicians/modes and multiple plans sharing a visit remain allowed; the link does not establish clinical suitability or sufficient combined duration. Source/target changes return 409; unchanged associations return 400.

The original `ProcedureRecord.appointmentId` remains immutable. Hydrated workflows and summaries add `effectiveAppointmentId` and `scheduledAppointment`; an explicit removed link stays null rather than falling back to the original. Patient projections contain no scheduling events, reasons, actor IDs, revisions or retry tokens. New completion snapshots are separate from the current linked visit, which can later reflect ordinary appointment changes.

Canonical lowercase UUIDs bind actor, procedure and normalized command. Exact replay occurs after authorization but before source/state/eligibility checks, returning the original event plus current context. Events and receipts reject updates/deletion. Link evidence, receipt, audit and generic patient activity commit atomically. Link changes do not edit appointments, resource reservations, original plans, agreements, completion evidence or invoice sources. Booking a new visit is a separate existing workflow; it does not automatically attach a plan.

These records capture a clinician's explanation and a reported patient decision. They are not an electronic-signature workflow or a certification of legally sufficient informed consent. There is no automatic treatment recommendation, drug-warning validation, laboratory connection or interpretation of report contents. Long clinical text fields have an 8,000-character limit.

- `GET /knowledge` → published `KnowledgeArticle[]` (public).
- `GET /knowledge/manage` → all `KnowledgeArticle[]` (clinician).
- `POST /knowledge {title,category,body}` → draft `KnowledgeArticle` (clinician).
- `PATCH /knowledge/:id {title?,category?,body?,status?}` → `KnowledgeArticle` (clinician). Edited content becomes draft unless explicitly reapproved with `status:'published'`.

Billing corrections require a current 64-hex revision, UUID request ID and trimmed 1–1,000 character reason. Reasons, attributed histories and before/after values are explicitly shared with the patient. Safe histories omit internal account/request IDs. A correction preserves invoice number, issue date, patient-name snapshot and procedure linkage. `issuedCharges` retains original line items and total; `invoice` contains current corrected charges and net paid. `payments` retains all originals, while `reversals` identifies excluded entries. Correction commands bind the request ID to the actor, operation, invoice, payment and normalized payload, excluding the expected revision. A procedure can have one linked invoice. It must belong to the invoice patient and must not be cancelled when linking a new invoice. Linked invoices include `procedureId` and the original `procedureTitle` snapshot. Linking is immutable and commits with invoice creation, sequence allocation, audit and patient activity.

Procedure estimates never populate a charge automatically: staff enter the agreed line items and amounts explicitly. Planning/completing a procedure does not create an invoice; creating an invoice does not record a payment. Cancelling a procedure does not change an existing charge or create a refund. Payment collection, refunds, tax calculation and external reconciliation require separate clinic processes.

## Knowledge authoring and version history

All `/knowledge-authoring` routes require an active administrator or doctor session. Current account/session/MFA state is rechecked inside the transaction; temporary-password accounts, patients and reception are denied. Reads are private, uncached and audited. Public article readers never receive these histories, private notes or command identifiers.

- `GET /knowledge-authoring?q=&status=&page=&pageSize=` → `KnowledgeAuthoringPage`. Status is `all` (default), `draft` or `published`; search is a literal substring with ASCII case folding. Pages are positive integers up to 1,000,000 and clamp to the last page. Page size is 10, 25 (default) or 50. Rows omit full bodies and include the current version number and revision.
- `GET /knowledge-authoring/:id` → `KnowledgeAuthoringDetail`: current article, revision, current version, current attributed publication or null, latest 25 change events and total event/version counts.
- `GET /knowledge-authoring/:id/versions?page=&pageSize=` → newest-first `KnowledgeVersionPage`.
- `GET /knowledge-authoring/:id/versions/:versionId` → one same-article `KnowledgeVersion`.
- `GET /knowledge-authoring/:id/history?page=&pageSize=` → newest-first `KnowledgeHistoryPage`.

Queries are strict. Detail and exact-version reads accept no query parameters. Unknown articles/versions return `404`. Versions distinguish newly attributed saves from `legacy-snapshot`/`legacy-current` imports. Legacy recorded author/date/status are preserved separately; missing action authorship, reasons and timestamps remain null.

New commands use strict JSON bodies. `fields` contains required trimmed `title`, `category` and `body` with limits 300/100/30,000 characters. `requestId` is a UUID; existing-article commands require the current 64-hex `expectedRevision`. Optional ordinary change notes are at most 1,000 characters. Publishing requires `reviewed:true`.

- `POST /knowledge-authoring {fields,publication,reviewed?,reason?,requestId}` → `KnowledgeAuthoringMutation`, `201` new or `200` exact replay. Publication is `draft` or `published`; creation and optional approval commit together.

- `POST /knowledge-authoring/:id/publication {published,reviewed?,reason?,requestId,expectedRevision}` → mutation. Explicitly publishes or withdraws the current content without creating a content version.
- `POST /knowledge-authoring/:id/restore {versionId,confirmed:true,reason,requestId,expectedRevision}` → mutation. Requires a same-article historical version and a 3–1,000-character reason. Always creates a new draft with source attribution, even if its text equals current text; restoring the current version is rejected.

Mutation responses contain `{detail,event,version}`. `event` and `version` identify the exact original accepted command; `detail` is current and may include later changes. Request keys bind actor, operation, target, revision and normalized payload. After checking current permission, exact replay is resolved before stale-state checks. Changed key intent or stale revisions return `409`; no-op commands return `400` except explicit historical restoration. Projection, snapshots, versions/events, receipt and audit commit atomically.

Legacy `/knowledge` and `/knowledge/manage` arrays remain compatible. Legacy creation still ignores extra status fields and creates a draft; PATCH retains partial-field and explicit-status behavior. Both write through the atomic versioned writer, but legacy requests have no automatic retry or stale-edit protection without the new command contract. Existing repeated identical legacy PATCH requests remain accepted and record an attributed action without fabricating a content change.

- `GET /public-library/:articleId` → `PublicArticle`: `id`, `title`, `category`, full plain-text `body`, `authorName` and `updatedAt`. Missing, draft and malformed identifiers have the same generic `404`; extra query parameters return `400`. IDs are stable across title changes and republication.

These endpoints are public, including for temporary-password sessions. They never include historical revisions, draft text, arbitrary stored fields or session/patient data. The existing `/knowledge` array remains compatible and explicitly projects its published fields, including `status:'published'`.

Document routes `/library` and `/library/:articleId` are outside the `/api` prefix. They serve initial public HTML, then hydrate the same shared React view. Real anchors, a GET search form and pagination remain usable without JavaScript. Unavailable articles and invalid document routes/queries return HTML `404` with no article details. Noncanonical case, trailing-slash and encoded path variants are rejected. In Express/production serving, known private SPA routes retain their shell response and access guards; unknown pages, `/index.html` and missing assets return `404`. Vite preserves its development fallback outside the forwarded `/library` routes.

Public library documents, JSON, sitemap and robots responses use `Cache-Control:no-store`; public content responses do not use automatic ETags. Withdrawal is checked on every request, including conditional requests. This prevents stale server responses; it cannot retract a page already downloaded by a reader or an external search engine.

Page titles, descriptions, canonical links and Open Graph/Twitter metadata derive from approved public fields. Absolute URLs use validated configuration, never request Host or forwarded headers. Indexing requires production mode, no demo data, a configured public origin and explicit opt-in. Search results are always noindex; unfiltered pagination may be indexed. `/sitemap.xml` lists only `/library` and current published article addresses when indexing is enabled, otherwise an empty URL set. `/robots.txt` permits fetching HTML so crawlers can observe noindex and excludes API crawling; it is not an access control. All other HTML routes remain noindex. See `DEPLOYMENT.md` for the optional publication settings.

## Administrator expenses and clinic reports

All endpoints in this section require an active administrator session. Other roles are denied, including doctors and reception. Reads and CSV downloads use the same authorization and `Cache-Control: no-store`.

- `GET /expenses?from=&to=&category=&status=` → `ClinicExpense[]`, ordered by incurred date newest first. Required `from` and `to` are real `YYYY-MM-DD` dates, ordered with at most 366 inclusive days. Optional status is `recorded | voided`; omission includes both. Optional category is one of `supplies | equipment | rent | utilities | staff | services | other`.
- `POST /expenses {incurredDate,category,description,amountPaise,reference?,requestId}` → `ClinicExpense` with `201`; an identical retry returns the original with `200`. `requestId` is a required UUID; reusing it with changed normalized fields returns `409`. Amount is an integer from 1 to 1,000,000,000 paise. Description requires 1–300 characters; reference allows up to 200. The incurred date must be a real calendar date and cannot be in the future relative to Asia/Kolkata. Authorship and recording time come from the server.
- `POST /expenses/:id/void {reason}` → updated `ClinicExpense`. The required reason has a 1–1,000 character limit. An identical repeated void returns the existing history; a different reason after voiding returns `409`. The original entry is never changed or deleted. Recording and voiding each commit with their audit entry.
- `GET /insights?from=&to=` → `ClinicInsights`. Uses the same required date range and 366-day limit; future reporting dates are allowed to inspect scheduled appointments. Includes `totals`, `appointmentsByStatus`, `appointmentsByMode`, `expensesByCategory`, `collectionsByMethod` and ascending zero-filled `daily` rows, with `timezone:'Asia/Kolkata'` and `generatedAt`.
- `GET /insights/export?from=&to=` → an authenticated CSV attachment generated from the same aggregation function. Columns are `section,date,metric,dimension,count,amountPaise`. CSV escaping protects quoted content and formula-like prefixes. Exports omit patient identities, account names, individual expense descriptions and references.

`ClinicExpense` preserves the request ID, original amount/category/date/description/reference, creating account ID/name and timestamp. It adds derived `status` and nullable `void` containing the immutable void ID, reason, recording account and date. There is no edit, delete, automatic replacement, payment initiation or bank-reversal operation.

Report appointment counts use the scheduled date and current status; distinct patients include all matching appointments, including cancellations/no-shows. Invoices use current corrected amounts at their original issue timestamp converted to clinic date. Collections exclude currently reversed erroneous entries and use original payment recording timestamps, which may relate to invoices issued outside the selected range; actual external receipt dates are not separately stored. Expenses use their incurred date and exclude currently voided entries. `issuedInvoiceOutstandingPaise` is the current unpaid balance on invoices issued in the range, not an as-of historical balance. Reports do not infer profit, tax, clinical outcomes or observed treatment adherence. JSON and CSV are separate current snapshots; data can change between requests.

## Patient details and allergy corrections

- `GET /patients/:id/profile` → `PatientProfile {patientId,demographics,revision,changes}`. All staff may read demographic history and editing revision. Patients may read only their own current demographics, with `revision:null` and `changes:[]`. The response never includes allergy fields or allergy-derived revisions.
- `PATCH /patients/:id/profile` accepts full `{name,email,phone,dob,gender,reason,expectedRevision,requestId}` from staff. Name1–300, email valid or empty (max254), phone7–30, DOB real nonfuture date or empty, gender0–50, reason1–1000. Whitespace is trimmed and email lowercased. Returns current `PatientProfile`. Each changed record preserves prior/current demographic values, staff identity, reason and timestamp. Reasons are staff-only. Empty or unchanged corrections return 400.
- `GET /patients/:id/allergies` → `PatientAllergyHistory {patientId,current:{status,text},revision,changes}` for clinicians or the owning patient. Patients receive null revision; reception is denied. Safe changes include before/after status/text, shared reason, doctor ID/name and timestamp, without account IDs or request IDs.
- `POST /patients/:id/allergies` requires a linked clinician and `{status,text,reason,expectedRevision,requestId}`. Status is `not-recorded`, `none-known` or `recorded`; text is1–8000 characters for `recorded` and empty otherwise. The reason (1–1000) is explicitly shared with the patient. Returns current history; unchanged clinical values return 400.

Both write families require a UUID and current64hex revision, use separate revision streams, and support exact actor-bound replay before stale/no-op checks. Reusing a correction key across actors, patients, operations or normalized payloads conflicts. Current patient changes, immutable events, request receipts and audit commit in one transaction. Concurrent changes in the same stream return409, while a demographic correction does not invalidate an allergy editing token or reveal that token to reception.

The current Patient projection adds `allergyStatus`; nonempty legacy allergy text maps to `recorded`, otherwise `not-recorded`, unless an explicit later clinician event states `none-known`. No legacy author or verification event is invented. Reception projections omit the status and retain empty `allergies` only for backward compatibility. These core corrections remain available when optional modules are paused. Login names/emails, account linkage, and historical patient-name snapshots in appointments, notes, plans and invoices remain unchanged. Patient-facing care summaries include current details/status and safe `allergyHistory`, but exclude demographic correction history and reasons.

## Consumable inventory

All inventory routes allow staff reads (`admin`, `doctor`, `receptionist`) and administrator mutations. Patients and temporary-password sessions cannot access inventory. No operation creates a charge, expense, prescription or patient association.

- `GET /inventory/items?search=&active=true|false|all&stock=low|expired|expiring-soon` → `InventoryItem[]`; active items by default. Search matches the catalogue; stock filters select items with the corresponding condition.
- `GET /inventory/items/:id` → `InventoryDetail {item,lots,itemChanges}`. Includes immutable catalogue snapshots with author, reason and date, newest first.
- `GET /inventory/items/:id/movements?limit=&cursor=` → `InventoryLedger {items,nextCursor}`; newest first, default 50 and maximum 100. Cursors are opaque movement IDs scoped to the item.
- `POST /inventory/items` accepts `{sku,name,category,unit,reorderLevel,requestId}` → `201 InventoryDetail`; an exact retry returns `200`.
- `PATCH /inventory/items/:id` accepts `{name?,category?,reorderLevel?,active?,reason,expectedRevision,requestId}` → `InventoryDetail`. SKU and unit are immutable. Edits retain an attributed catalogue snapshot; archive/reactivation preserve all stock history.
- `POST /inventory/items/:id/receipts` accepts `{quantity,lotCode?,expiryDate,reason,reference?,expectedRevision,requestId}` → `201 InventoryMutation {detail,movement}`. `expiryDate` is an exact calendar date or `null`. Every receipt creates its own immutable lot, even when supplier lot labels repeat.
- `POST /inventory/lots/:id/use` accepts `{quantity,reason,reference?,expectedRevision,requestId}` → `InventoryMutation`. The item must be active, the lot must not be expired, and sufficient stock must remain.
- `POST /inventory/lots/:id/adjust` accepts `{countedQuantity,reason,reference?,expectedRevision,requestId}` → `InventoryMutation`. It records the observed whole-unit balance, deriving the signed adjustment from the current lot balance. A zero adjustment still records the count. Inactive and expired lots can be reconciled.

Categories are `dressings`, `protective-equipment`, `instruments`, `cleaning`, `office`, `other`. Units are `piece`, `pair`, `pack`, `box`, `bottle`; they count whole units without conversions. SKU is normalized uppercase, 1–50 characters: a leading letter/digit followed by letters, digits, periods, underscores or hyphens. Names are 1–150 characters; lot codes up to 100; reasons 1–1000; references up to 200. Receipt/use quantity is an integer from 1 to 1,000,000. Counts and lot/item balances are bounded from 0 to 1,000,000,000; reorder thresholds from 0 to 1,000,000.

`InventoryItem` exposes on-hand, unexpired, expired and expiring-soon quantities, a low-stock flag and a revision. A lot is expired when its recorded expiry date is before today's Asia/Kolkata date. Expiring soon covers today through 30 days ahead, inclusive. Unknown expiry is explicitly `null`; it contributes to unexpired quantity without claiming suitability for use. Low stock means an active item's unexpired balance is at or below its reorder threshold. Already-expired receipts may document existing physical stock but cannot subsequently be used.

Stock balances derive from immutable movements; `balanceAfter` is the recorded balance of that lot after the event, not a current balance or item total. Catalogue originals, changes, lot metadata and movements are retained. Revisions include catalogue/stock changes and the clinic date, so a day rollover requires refresh before a new stock operation. Global request UUIDs are bound to the actor, operation and normalized business payload. Exact retries resolve before revision checks and return the original event with current detail; reusing a key for different input or an account conflicts. Revision/balance checks, source events, request receipts and audit entries commit in one transaction. Failed audits do not leave partial stock changes.

## Clinic rooms and equipment

These endpoints are staff-only (`admin`, `doctor`, `receptionist`). Catalogue and maintenance mutations require an administrator; all staff can assign resources to existing appointments. No resource information is added to the patient-facing appointment, clinical workflow or care-summary types.

- `GET /clinic-resources?active=true|false|all` → `ClinicResource[]`, all states by default. Each resource has immutable kind `room|equipment`, capacity `1`, name, location, operational notes, active state and revision.
- `GET /clinic-resources/:id` → `ResourceDetail {resource,changes,closures}` with attributed catalogue changes and maintenance history.
- `POST /clinic-resources {name,kind,location?,notes?,requestId}` → `201 ResourceDetail`, or `200` on exact retry. Names are unique case-insensitively, including archived items; name1–100, location0–200, notes0–1000.
- `PATCH /clinic-resources/:id {name?,location?,notes?,active?,reason,expectedRevision,requestId}` → current detail. Kind and capacity cannot change. Archive preserves history and rejects open allocations, including overdue open visits, or completed reservations whose recorded interval has not ended.
- `POST /clinic-resources/:id/closures {startDate,endDate,startTime,endTime,reason,expectedRevision,requestId}` → `201 ResourceDetail`, or `200` on exact retry. Dates are inclusive, today through 365 days ahead in Asia/Kolkata; both times are null for all-day closure or ordered `HH:mm` values repeated daily. No overnight windows. Active reservations ending after now cannot overlap new maintenance.
- `POST /clinic-resources/:id/closures/:closureId/cancel {reason,expectedRevision,requestId}` → current detail. Cancellation preserves the original maintenance window and attributed cancellation.
- `GET /appointments/:id/resources` → `AppointmentResourceContext {appointment,resourceIds,revision,canAllocate,canRelease,resources,history}`. Appointment is an operational snapshot without the clinical reason. Availability excludes this visit's own claims and reports `available|inactive|maintenance|reserved`.
- `PUT /appointments/:id/resources {resourceIds,reason,expectedRevision,requestId}` → current context. Atomically replaces the full selection of zero to eight unique resource IDs. Add/replace is allowed for future scheduled visits or checked-in/in-consultation visits before their scheduled end. Clearing an existing selection is allowed for any still-open visit. Terminal history is read-only.
- `GET /resource-reservations?from=&to=&resourceId=` → `{from,to,timezone:'Asia/Kolkata',reservations}`. Real ordered dates cover at most 31 inclusive days. Current retained reservations include completed recorded intervals; cancelled/no-show allocations are released. Rows contain operational visit and resource identities, without clinical notes.

All writes require a canonical UUID bound to actor, operation, target and normalized intent. Exact replay precedes revision and no-op checks; reasons require 1–1000 characters. Revisions cover relevant catalogue, maintenance and reservation changes. Immutable history, replay receipts, current claims and audit records commit together. Resource intervals are half-open: a booking ending at 10:00 permits another beginning at 10:00. Every item covers the visit's full recorded duration, with a 30-minute fallback for legacy appointments.

`PATCH /appointments/:id` moves retained allocations atomically with an explicit reschedule, preserving custom minutes or adopting the selected doctor's current default duration. Resource conflict returns 409. Patient responses use a generic message that does not identify other patients, individual resources or maintenance; staff responses identify the unavailable resource. Authorized `GET /slots` calls with `excludeAppointmentId` filter those conflicts. Public/new bookings and waitlist conversions remain unallocated until staff explicitly assign resources. Cancellation/no-show releases claims; completion retains the recorded interval. Status and movement history remain immutable. These are scheduled reservations, with no automatic occupancy extension, consumable movement or invoice operation.

## Paginated record search

The additive `/search/*` endpoints return `SearchPage<T> {items,page,pageSize,total,totalPages}`. `page` defaults to 1 and accepts 1–1,000,000; `pageSize` defaults to 25 and accepts 1–100. The server clamps the requested page to the last available page; an empty result has page 1 and totalPages 1. COUNT and limited SELECT use one SQLite read transaction. Separate requests show current data, with no guarantee of stable row positions after concurrent additions or edits.

- `GET /search/patients?q=&page=&pageSize=` is staff-only. Returns demographic `PatientDirectoryItem` rows (id, name, email, phone, date of birth, gender, registration timestamp), newest registration first with descending ID as a deterministic tie-breaker. Search matches name, email, phone or patient ID. Allergy fields, clinical status and private correction history neither appear nor influence matches/counts.
- `GET /search/appointments?q=&from=&to=&doctorId=&patientId=&status=&mode=&page=&pageSize=` is staff-only. Dates filter the scheduled clinic date and may be one-sided. Status accepts any appointment status or `waiting` for scheduled/checked-in. Mode is `in-person|online`. Search matches the saved patient-name snapshot or current patient name/contact/ID; returned `Appointment` values retain original snapshots. Sort is date/time/ID ascending.
- `GET /search/audit?q=&actor=&action=&entityType=&entityId=&from=&to=&page=&pageSize=` is administrator-only. General text searches visible audit fields and entry ID. Actor/action are literal substring filters; record type/ID are exact. Date bounds include the whole selected IST days, compared against the stored UTC timestamps. Sort is timestamp/ID descending. There is no 500-entry ceiling and reads do not generate recursive audit entries.

Text searches are trimmed and capped at 200 characters; identifiers at 300. Real `YYYY-MM-DD` dates are required, ordered when both bounds are supplied. Unknown, duplicate, malformed and oversized parameters return 400. Patients and temporary-password sessions cannot use these staff endpoints. Every result uses `Cache-Control: no-store`. SQL parameters and `instr` treat percent signs, underscores, quotes and backslashes literally. Built-in SQLite lowercase matching folds ASCII letters; it is not Unicode case-folding or fuzzy search.

Filtering, counting, sorting and limiting execute in SQLite, and only returned rows are decoded in application memory. Date/doctor/patient/status/mode and audit date/record indexes support common filters; arbitrary substring matches may still scan candidates. No response size or constant-time full-text search guarantee is implied for older compatibility APIs: `/patients` and `/appointments` still return arrays. `/audit` keeps its original latest 500 array contract but now applies that limit in SQL.

## Staff attendance

Attendance belongs to a staff account, not a doctor profile or patient. Patients and temporary-password sessions cannot access these endpoints. Staff can read only their own entries; administrators can inspect and correct all staff, including inactive accounts. Staff identities contain only ID, name, role and active status. Reads use `Cache-Control: no-store`.

- `GET /attendance/me` → `AttendanceContext {staff,revision,openShift,serverNow,timezone}` for the current account.
- `GET /attendance/staff` and `GET /attendance/staff/:id/context` are administrator-only; the latter supplies the target account revision for recording missed attendance.
- `POST /attendance/clock-in {requestId,expectedRevision}` starts the current account's entry using server time. New entries return 201; exact retries return 200.
- `POST /attendance/shifts/:id/clock-out {requestId,expectedRevision}` ends the caller's own open entry using server time; its expected revision comes from `/attendance/me`.
- `POST /attendance/shifts {userId,startedAt,endedAt,reason,requestId,expectedRevision}` records a missed closed interval; administrator-only, using the target account-context revision.
- `GET /attendance/shifts/:id` → `AttendanceDetail {shift,events}` for the owner or an administrator. Missing and forbidden entry IDs return 404 to other staff.
- `POST /attendance/shifts/:id/corrections {startedAt,endedAt,reason,requestId,expectedRevision}` records an administrator correction using the shift revision. It can close an open entry or change a closed interval, but cannot reopen or change the staff identity.
- `POST /attendance/shifts/:id/void {reason,requestId,expectedRevision}` marks an erroneous entry void using the shift revision. Voiding is terminal, preserves history and releases an open interval.

All mutations return `AttendanceMutation {shift,event}`: the current effective shift and the immutable receipt for that exact command. Events preserve the request UUID, expected revision, before/after times, reason and actor identity. Canonical lowercase UUIDs are bound to actor, operation, target and normalized payload. Exact retries precede current-state/revision checks after authorization; changed commands return 409. Account revisions change with any attendance event for that account; shift revisions change with that entry's events. Uncertain client responses must retain the same payload and UUID until confirmed.

Timestamp inputs are real canonical UTC ISO strings with milliseconds. Times cannot be future, the end cannot precede the start, and a completed interval cannot exceed 36 hours. A zero-second interval is allowed for rapid clocking. Staff can have one open entry; nonvoid intervals cannot overlap, while adjacent intervals are allowed. An open entry older than 36 hours requires administrator correction or voiding. Logout, suspension and password changes never fabricate an end time. Reasons are required for administrator entries and changes, and are visible to the affected staff member.

`GET /attendance?from=&to=&userId=&status=&page=&pageSize=` returns `AttendanceReport`, extending `SearchPage<AttendanceShift>` with the applied filters, timezone, generation time, whole-result revision and totals (`closedShiftCount`, `recordedSeconds`, `openShiftCount`, `voidedShiftCount`). Dates are inclusive IST **start dates**, ordered and at most 366 days. Completed intervals contribute their entire floored elapsed seconds to their effective start-date cohort; open/voided entries contribute no time. Administrators may omit `userId` for all staff; other staff are restricted to their own ID, with another ID rejected as 403. Status is `all|open|closed|voided`. Pages default to 1 and 25 rows, with maxima 1,000,000 and 100; requests clamp to the last page. Sort is effective start timestamp descending, then ID descending. Counts, totals, revisions and page rows share one database snapshot.

`GET /attendance/export.csv` is administrator-only and takes the same date/user/status filters plus `expectedRevision`, without page parameters. It exports effective attendance fields and status, omitting correction reasons and account contact/clinical data. The revision covers the full filtered report, independent of pagination. Changed reports return 409; more than 10,000 matches return 422 rather than truncating. Confirmed responses use CSV content type, attachment disposition and `X-Attendance-Revision`; spreadsheet formula prefixes are escaped. No attendance operation changes payroll, expenses, patient activity or appointment availability.
