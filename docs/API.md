# Application contract

All paths below start with `/api`. JSON errors use `{error: string}` and an appropriate HTTP status. List endpoints return arrays unless an object shape is stated. Calendar dates use `YYYY-MM-DD`; schedule times use `HH:mm` in `Asia/Kolkata`. Event timestamps and session expiry values are ISO timestamps.

Requests that change state use JSON. Except for login, registration, recovery-token redemption and the separate MFA challenge flow, they require an authenticated session and the session’s `X-CSRF-Token` header. MFA verification/cancellation instead requires its short-lived challenge cookie and `X-MFA-CSRF-Token`. Browser-origin checks also apply. The session cookie is HTTP-only, uses `SameSite=Lax`, and is secure in production. Roles, account status and patient ownership are enforced by the server, not only the interface.

Core models are in `shared/types.ts`; scheduling, waitlist, identity, operations, clinical workflows, PDF reports, follow-up reviews/assignments and activity models are in `shared/scheduling.ts`, `shared/waitlist.ts`, `shared/identity.ts`, `shared/operations.ts`, `shared/clinical.ts`, `shared/documents.ts`, `shared/follow-up.ts` and `shared/activity.ts`.

Demo accounts use `DemoClinic2026!` with `doctor@derma.demo`, `reception@derma.demo`, `patient@derma.demo` and `admin@derma.demo`. Demo records are synthetic and cannot be used as a production database.

## Authentication and account lifecycle

- `GET /session` → `Session` (`user`, optional `csrfToken`, `demoMode`). Account data includes normalized `active` and `mustChangePassword` flags.
- `POST /auth/login {email,password}` → `Session` with `200`, or `MfaChallenge` with `202` when a second factor is enrolled. A challenge grants no signed-in session. Inactive accounts cannot sign in. A temporary-password account receives a restricted session until its password is changed.
- `POST /auth/register {name,email,password,phone,dob,gender}` → `Session`; creates a new patient and patient account. Email and date of birth are required.
- `POST /auth/logout` → `{ok:true}`; ends the current session.
- `POST /auth/password {currentPassword,newPassword}` → `{ok:true}`. Passwords require 12–128 characters, and the new password must differ from the current one. Clears the initial-password requirement, ends other sessions and invalidates outstanding recovery grants.
- `GET /auth/sessions` → `AccountSession[]` for the current account: opaque `id`, `createdAt`, `expiresAt`, `current`, and coarse browser `label`. Sessions expire twelve hours after creation.
- `POST /auth/sessions/revoke-others {}` → `{ok:true,revoked:number}`.
- `DELETE /auth/sessions/:id {}` → `{ok:true}`; only the account’s own sessions can be revoked. Revoking the current session also clears its cookie.
- `GET /accounts?search=&role=` → `ManagedAccount[]` (administrator). Search matches name/email; role is one of `admin`, `doctor`, `receptionist`, `patient`.
- `PATCH /accounts/:id {name?,role?,doctorId?:string|null,active?}` → `ManagedAccount` (administrator). Role, linked-profile or active-status changes revoke all target sessions and recovery grants. A doctor role requires a valid doctor profile; a receptionist cannot have one. Patient/staff conversion and patient relinking are rejected. Self-suspension is rejected, and removing the final active administrator returns `409`.
- `POST /accounts/:id/recovery {identityVerified:true}` → `RecoveryGrant` (`token`, `expiresAt`) (administrator, active target account only). The 64-character token is returned once, stored only as a digest, expires after thirty minutes and replaces any earlier grant for that account. Issuing a grant does not itself end existing sessions.
- `POST /auth/recover {token,password}` → `{ok:true}` (no session or CSRF token required). Redeems a valid grant once, changes the password, clears the initial-password requirement and ends all target-account sessions and recovery grants. It does not sign the account in. Invalid, expired and inactive-account grants use a generic error.

Recovery links are shared manually after the clinic verifies identity. The frontend reads the token from `/recover#token=...` and removes it from the address bar. The server does not send recovery email or SMS. Authentication, password changes and recovery actions are rate-limited.

Authentication limits use persistent, independent fifteen-minute windows. Login allows twenty requests per network address and ten failed passwords per normalized email; the eleventh password attempt is blocked even if correct. Registration, password changes and recovery-link issuance allow ten network requests per operation; recovery redemption allows twenty. Schema-invalid JSON requests that reach the route consume the network budget only; malformed JSON and requests rejected by earlier origin, content-type or session guards never reach these counters. Unknown, inactive and wrong-password accounts return the same `401` response and consume the same identifier failure budget. A successful password step clears its identifier failures only after current credentials are revalidated and the session or MFA challenge commits. It does not reset network limits or the separate MFA proof budget.

An exhausted network or password-failure budget returns `429 {error:string}` with an integer `Retry-After` header giving the remaining seconds. Rejected attempts do not extend the fixed window. Limits survive process restart and are shared by application instances using the same database. Forwarded addresses are used only with the configured trusted proxy.

Failed-password audit entries are bounded to the first and tenth failure per identifier window, plus the first rejection per exhausted budget. They use record type `auth-security`, actor `Unauthenticated`, and keyed digests rather than raw submitted email/network addresses. Passwords, tokens and request bodies are excluded. Registration commits patient/account creation, audit and session atomically; logout commits current-session revocation, pending MFA setup removal and `signed out` audit atomically. Cookies change only after those commits. Network admission is a separate transaction: an admitted request remains counted if later validation, audit or session writes fail, while the associated identifier/audit or account/session changes roll back together.

Restricted temporary-password sessions can change their password, sign out or manage their own sessions. They cannot read private clinic/patient data or perform workspace operations. Public discovery/settings/availability/knowledge reads remain available.

## Optional authenticator MFA

Types are in `shared/mfa.ts`. MFA requires a configured `MFA_ENCRYPTION_KEY` (64 hexadecimal characters); accounts remain unenrolled until explicit setup. Ordinary password login remains available for unenrolled accounts. All MFA responses are private/no-store, and routes reject unknown query/body fields. Own-account management is unavailable to temporary-password sessions until password rotation completes.

- `GET /auth/mfa` → `MfaStatus`: key availability, enabled state/date, remaining recovery-code count, revision, pending metadata and the latest 100 sanitized security events. No secrets or proof values are returned.
- `POST /auth/mfa/enrollment/prepare {currentPassword,expectedRevision,requestId}` → `MfaPreparation`. Verifies the password and stages a secret, authenticator URI and ten recovery codes for ten minutes. A preparation does not activate MFA. New preparation replaces prior pending material.
- `POST /auth/mfa/enrollment/confirm {pendingId,code,savedRecoveryCodes:true,expectedRevision,requestId}` → `MfaMutation`. Requires the staged authenticator's code and explicit saved-code acknowledgment. Activates the factor and recovery hashes, consumes the accepted time step and destroys pending secret material.
- `POST /auth/mfa/recovery-codes/prepare {currentPassword,proof,expectedRevision,requestId}` → `MfaPreparation`. Password and existing factor are required. Stages replacement codes while the previous set remains active, except any old recovery code consumed as proof. The confirmation uses the returned `status.revision`, which can differ from the preparation's original source revision.
- `POST /auth/mfa/recovery-codes/confirm {pendingId,savedRecoveryCodes:true,expectedRevision,requestId}` → `MfaMutation`. Checks the current revision and same session/security context before replacing the entire active recovery-code batch.
- `POST /auth/mfa/disable {currentPassword,proof,expectedRevision,requestId}` → `MfaMutation`. Verifies both factors and removes enrolled material. It does not change the password.

`proof` is `{method:'totp'|'recovery-code',code:string}`. Canonical request UUIDs bind actor, session, operation and an HMAC of the normalized payload. Exact completed-command replay returns the original sanitized event plus current safe status before stale/consumed-proof checks. Preparation replay additionally verifies the current password and only returns the same encrypted pending material while unexpired and unsuperseded. Changed command intent is `409`; stale revision is `409`; expired/superseded preparation is `410`. All successful security mutations and audit records commit atomically. Factor changes end other sessions and challenges; the currently proven session remains valid.

For enrolled accounts, correct password login returns a five-minute `MfaChallenge` containing `mfaRequired:true`, intended `accountId`, a separate CSRF token and expiry. Its random token is in an HTTP-only `derma_mfa_challenge` cookie, scoped to `/api/auth/mfa`; only its digest is stored. The presented prior full session is ended/cleared.

- `GET /auth/mfa/challenge` restores valid challenge metadata without authenticating the account.
- `POST /auth/mfa/verify {proof}` with challenge cookie and `X-MFA-CSRF-Token` → full `Session` only after a valid one-use proof. Session creation, challenge/code consumption and audit commit together; the full session cookie is emitted after commit.
- `POST /auth/mfa/challenge/cancel {}` with the challenge credentials → `{ok:true}` and clears the challenge.

Invalid/expired challenges return `401`; invalid proof returns `400`; exhausted attempts return `429`. A durable account budget limits failures to ten per fifteen-minute window across challenges and restarts. Accepted authenticator steps and recovery codes cannot be reused. Lost verification responses can be reconciled through `/session` only when its user matches the challenge's intended account; otherwise restart password authentication with a fresh proof. Challenge metadata must never replace full-session state or CSRF credentials.

Password change, recovery and account access changes invalidate pending MFA preparations/challenges. Password recovery preserves enrolled MFA and does not log the user in. There is no administrator HTTP reset endpoint. The local operator reset requires explicit identity-verification acknowledgment and a reason, removes factors, ends sessions and requires password rotation. Key and reset procedures are documented in `DEPLOYMENT.md`.

## Administration and public configuration

- `GET /users` → normalized account data (administrator; retained for staff and portal setup).
- `POST /users {name,email,password,role,doctorId?}` → `User` with 201 (administrator). The compatibility route commits the user and creation audit together. Repeating a successful creation with the same email returns 409.
- `POST /users/create {requestId,name,email,role,doctorId,reviewedConfirmed:true,password}` → `{receipt:{actorId,requestId,account}}` with 201 for creation or 200 for an earlier success. The account snapshot includes the original ID, name, normalized email, role, linked profile if present, `active:true` and `mustChangePassword:true`.
- `POST /users/creation-outcome {requestId,name,email,role,doctorId,reviewedConfirmed:true}` → the same receipt with 200, or a definitive 409 with `{code:'STAFF_ACCOUNT_NOT_CREATED',actorId,review,message}`. This route rejects extra fields, including a password. If the request has never been recorded, the check closes it atomically. A delayed creation with that UUID receives the same refusal. A fresh UUID and initial password are required to intentionally start again.
- `GET /doctors` → `Doctor[]` (public). Each profile includes its current `appointmentDurationMinutes` and safe `acceptingNewBookings` boolean. Paused profiles remain in the directory; private reasons/history/revisions are excluded.
- `POST /doctors {name,title,qualifications,specialties,experience,fee,bio,languages,color?}` → the saved profile with 201 (administrator). This compatibility route commits the profile and creation audit together. Each delivery creates a new profile.
- `POST /doctors/create` takes the same flat profile fields plus a UUID `requestId` and `reviewedConfirmed:true`. Returns `{receipt:{actorId,requestId,doctor}}` with 201 for a new profile or 200 for an exact retry by the creating administrator. The snapshot includes the original ID and public fields. Omitted color defaults to `#b3c7aa`. The order of specialties and languages is significant. A claimed UUID used by another administrator or with different normalized fields returns 409 without a receipt. A fresh UUID creates a distinct profile even when every detail matches. This route rejects extra fields and query parameters.
- `PATCH /doctors/:id` → the updated profile with 200 (administrator). This compatibility endpoint takes the full profile. Changed values, attributed history and update audit commit together. A no-op keeps the revision and records the compatibility audit. An old client can overwrite newer values because it supplies no revision. Settings uses the reviewed routes below.
- `GET /settings` → `ClinicSettings` (public fields only).
- `PATCH /settings` → `ClinicSettings` (administrator; compatibility API with partial clinic fields). Timezone remains `Asia/Kolkata`; module settings cover `intake`, `images` and `followUp`. Explicitly submitted fields merge into current settings under the write lock, with atomic legacy change history and audit. This unversioned API does not reject stale submitted fields. Unknown fields are stripped; a no-op creates no configuration change.
- `GET /audit` → `AuditEntry[]` (administrator).
- `GET /health` → `{status:'ok'}`.

Both reviewed routes require the same currently authorized administrator, UUID and normalized account details. A UUID claimed by another actor or different details yields a generic 409. An email already in use or an invalid profile linkage produces a recorded refusal on the reviewed creation route. Set `doctorId` to an existing profile for a doctor, an existing profile or `null` for an administrator, and `null` for a receptionist. The initial password accepts 12–128 characters and is used only when a new user is created. A successful replay with a different valid password returns the original receipt and leaves the credential intact. Use the outcome route after an interrupted response. Use `GET /accounts` for current roles, access and password-change status.

Disabling a module pauses its new activity. Existing records remain readable within the usual permissions. The clinic’s public `hours` string is descriptive; bookable hours are configured by scheduling endpoints.

## Reviewed doctor-profile edits

- `GET /doctors/:id/profile-context` → `{doctor,revision}` for the current administrator. The doctor contains the ID and stored public fields. The revision is an opaque 64-character lowercase hexadecimal string. Changes to booking availability, schedules and staff accounts have independent lifecycles.
- `POST /doctors/:id/profile-changes {profile,expectedRevision,requestId,reviewedConfirmed:true}` → `{receipt:{actorId,doctorId,requestId,expectedRevision,revision,before,after}}`. Supply every normalized profile field, including color and ordered specialty and language arrays. Use a new UUID for each deliberate edit. A new change returns 201. An exact retry returns the original receipt with 200 after later edits, including a change away from and back to the same values.
- A stale review or unchanged proposal returns 409 with `{code,actorId,doctorId,requestId,expectedRevision,profile}`. The code is `DOCTOR_PROFILE_CHANGED` or `DOCTOR_PROFILE_UNCHANGED`. The server retains that outcome for identical retries. Reusing a UUID for a different administrator, profile, source revision or change returns a generic 409. To retry an interrupted save, send its original command. To revise the proposal, fetch the current context and review the changes with a new UUID.
- `GET /doctors/:id/profile-history?page=1&pageSize=10` → `{items,page,pageSize,total,totalPages}` for administrators. Each newest-first entry includes the doctor ID, actor ID and name, time, source (`reviewed` or `legacy`) and before/after public fields. Page sizes are 10, 25 or 50. Existing profiles begin with empty edit history on upgrade. The public directory continues to serve only the current profile and booking information.

## Versioned clinic configuration

- `GET /clinic-configuration` → `{settings,profileRevision,modulesRevision,latestProfileChange,latestModulesChange}` (administrator).
- `POST /clinic-configuration/profile {profile,reason,expectedRevision,requestId}` → `{context,change,receipt}` (administrator; 201 new / 200 exact retry).
- `POST /clinic-configuration/modules {modules,reason,expectedRevision,requestId}` → the same result (administrator).
- `GET /clinic-configuration/history?scope=all|profile|modules&page&pageSize` → `{items,page,pageSize,total,totalPages}` (administrator). Defaults are all/1/25; sizes are 10, 25 or 50. Pages clamp to the current total, with stable newest-first timestamp/ID ordering and SQL-bounded materialization.

`profile` contains all public clinic fields except modules: name, tagline, phone, email, address, hours and timezone. Name is required (1–300 characters); tagline, phone, address and hours allow blank values up to 300 characters. Email is blank or valid, trimmed/lowercase and at most 254 characters. Timezone remains `Asia/Kolkata`. `modules` requires the three booleans `intake`, `images` and `followUp`. Reasons are trimmed 1–1000 characters, revisions are lowercase 64-character SHA-256 strings and request IDs are UUIDs. Reviewed routes reject unknown fields/query parameters and unchanged values.

Each scope has its own revision binding current canonical values and the latest immutable change identity. Edits to the other scope preserve the revision; changing away and back does not revive an old revision. A stale new request returns 409. An exact retry binds administrator identity, scope and the normalized complete request, including the original revision. It returns the original change/receipt alongside current context, even after later edits. Authentication, session/MFA, required password change and current administrator role are checked again inside the transaction before replay or mutation.

Change records contain a discriminated scope, before/after values, source (`reviewed` or `legacy`), private reason, actor display name and timestamp. The receipt contains requestId, actorId, scope, expectedRevision and changeId. Current public settings exclude these private records and metadata. Existing configuration has null latest changes until explicitly edited; no earlier authorship or reason is invented. The compatibility PATCH writes source `legacy` with null reason; updating both groups produces two changes in the same transaction. Settings, events, command receipt and audit save or roll back together. There is no history deletion or restore endpoint.

## Availability and appointments

- `GET /scheduling` → `SchedulingData` (`schedules`, `closures`, `timezone`, `bookingWindowDays`) (staff). Includes an effective schedule for every doctor, including defaults.
- `GET /schedules/:doctorId` → `DoctorSchedule` (staff).
- `PUT /schedules/:doctorId {durationMinutes,windows}` → `DoctorSchedule` (compatibility API; administrator, or doctor managing their own profile). `durationMinutes` is `15 | 20 | 30 | 45 | 60`. Each window is `{day,start,end,mode}`: day `0` is Sunday through `6` Saturday, and mode is `in-person | online | both`. Empty windows close all weekly availability. Sessions must not overlap on a day, even across different modes, and each must fit at least one appointment. Saved windows are sorted by day/start.
- `POST /schedule-closures {doctorId,startDate,endDate,startTime,endTime,reason}` → `ScheduleClosure` (administrator, or doctor for their own profile). `doctorId:null` applies to the entire clinic and requires an administrator. Both times `null` mean all day; otherwise the same start/end interval applies on each included date. End date must not precede start date or today. The end time must be later on the same day; overnight intervals are not supported.
- `DELETE /schedule-closures/:id {}` → `{ok:true}` (compatibility cancellation; administrator or the closure’s owning doctor). Removes the active booking restriction and retains cancellation history. An already absent/cancelled entry returns 404.
- `GET /slots?doctorId=&date=&mode=&excludeAppointmentId=` → available start-time strings. Public reads omit `excludeAppointmentId`; supplying it requires access to that appointment and excludes its current reservation when rescheduling. Optional mode is `in-person` or `online`. Signed-in patients’ own overlapping appointments are also filtered.
- `GET /appointments?date=&doctorId=` → `Appointment[]` (staff or owning patient).
- `POST /appointments {patientId?,doctorId,date,time,mode,reason,waitlistId?,patientConfirmed?}` → `Appointment` with `201` (staff or owning patient; compatibility endpoint). The server assigns the selected doctor’s current appointment duration. Linking `waitlistId` requires `patientConfirmed:true` and the matching patient, doctor, consultation mode and requested date window; normal slot checks still apply. This endpoint has no request-identity guarantee; interactive ordinary booking uses `/appointment-bookings` below.
- `PATCH /appointments/:id {status?,date?,time?,doctorId?,mode?}` → `Appointment`. Rescheduling is allowed only while scheduled and cannot be combined with a non-scheduled status change. Patients may reschedule or cancel their own scheduled appointments. Clinic states follow the allowed transition graph; only clinicians can start or complete a consultation.
- `GET /appointments/:id/calendar` → authorized `.ics` download, using the appointment’s recorded duration and IST start time.

Defaults are Monday–Saturday, 09:00–18:00, thirty-minute appointments and both consultation modes. Configured schedules may use other weekdays and multiple daily sessions. The booking horizon is currently 180 days; past times are never offered. The server checks full interval overlap for doctor and patient inside a transaction, including older appointments of a different length.

A schedule change or closure that invalidates existing future bookings returns `409`, leaving both availability and appointments unchanged. Existing bookings must be rescheduled or cancelled first. Changing a schedule alone preserves their duration. Explicit rescheduling adopts the selected doctor's current duration for ordinary visits; `durationPolicy:'custom'` preserves saved custom minutes. Legacy appointments without `durationMinutes` are treated as thirty minutes, and omitted policy means `schedule`. Removing a closure restores the hours allowed by the weekly schedule.

Temporary-password sessions receive anonymous slot availability: their patient-specific busy periods are not applied, and `excludeAppointmentId` is rejected until password rotation.

## Doctor new-booking status

- `GET /doctors/:doctorId/booking-status` → `{doctor:{id,name},acceptingNewBookings,revision,latestChange}` (administrator).
- `POST /doctors/:doctorId/booking-status {acceptingNewBookings,reason,expectedRevision,requestId}` → `{context,change,receipt}` (administrator; 201 new / 200 exact retry).
- `GET /doctors/:doctorId/booking-status/history?page&pageSize` → `{items,page,pageSize,total,totalPages}` (administrator). Defaults 1/25, sizes 10/25/50, page 1–1,000,000 clamped to the final page; stable newest timestamp/ID order with bounded SQL projection.

Missing persisted status means accepting, with no invented baseline event. Existing and newly created profiles retain this default. Status is independent of profile/account edits, weekly sessions and time off. A revision binds doctor identity, the accepting boolean and latest immutable status event, so changes away and back invalidate an older draft. Doctor names and unrelated schedule/profile changes do not invalidate it. A new no-op returns 400; stale source and reused request identifiers return distinct 409 errors. Commands reject unknown fields, trim the private reason to 1–1000 characters, require a lowercase 64-character revision and normalize UUIDs to lowercase.

Every private read/write/replay rechecks current administrator account, session, CSRF binding, password and MFA state under the transaction lock. Exact retry binds actor, doctor and normalized input including the original revision; it returns the original event/receipt alongside current context before stale/no-op checks. Changes retain doctor name, before/after booleans, reason, actor name and timestamp. Receipt fields are actorId, requestId, doctorId, expectedRevision and changeId. Status, event, receipt and audit writes commit or roll back together; history and command receipts are append-only.

A paused doctor rejects new ordinary/custom appointments, new recurring series, new waitlist requests and fulfillment, and transfers from another doctor with 409. Public new-booking slot reads return an empty array. Existing scheduled same-doctor visits remain reschedulable and can change duration under all existing time, overlap and resource rules. This exception is derived from the authorized stored appointment's doctor, patient and scheduled status, never a client boolean or batch exclusion list. Authorized existing-appointment slot queries retain those choices. Moving away to an accepting doctor remains possible. Patient records, appointments, resources, procedures, weekly sessions, time off, reminders and login access are not changed by a pause.

New-series previews bind the status event identity, including pause/resume changes away and back. Existing same-doctor series moves do not become stale merely because booking status changed. Successful ordinary-booking, custom-booking and series commands replay after a pause; ordinary waitlist fulfillment uses the same booking command described below. Compatibility `POST /appointments` has no retry identity. Existing waiting requests remain readable and withdrawable. Public projections, calendars and care summaries exclude private status evidence.

## Ordinary booking confirmations and retries

`POST /appointment-bookings {requestId,patientId,doctorId,date,time,mode,reason,waitlistId?,patientConfirmed?}` accepts all staff roles and the owning patient. Its JSON body and empty query are strict. The request ID is a UUID normalized to lowercase; identifiers and the required reason are trimmed and limited to 300 characters. Date/time must be real `YYYY-MM-DD`/`HH:mm` values. Mode is `in-person|online`; `patientConfirmed:true` is required with a waitlist ID. Custom duration fields are rejected. The existing booking horizon, full-interval conflicts, weekly hours, time off, doctor pause and waitlist rules apply to new attempts.

The result is `AppointmentBookingResult {appointment,booking,receipt}`, with `201` for a new booking and `200` for an exact replay. `appointment` is the current record. `booking` retains an immutable original appointment, its own ID, optional waitlist ID (null otherwise), patient-confirmation boolean, creator ID/name/role and creation time. `receipt` binds requestId, actorId, patientId, bookingId and appointmentId. Current appointment fields may differ after rescheduling, duration changes, cancellation or other clinic operations; the original confirmation does not change.

Request identity is unique within this endpoint and binds the actual actor, booking operation and full normalized input. Every attempt rechecks current session, CSRF, active account, required-password-change state, MFA and patient access under the write lock. Exact replay is resolved before current availability, doctor-pause, time-expiry or terminal-waitlist checks. Reusing an identity for another actor or payload returns `409` without a definitive outcome marker. The appointment, optional waitlist transition, original confirmation, command, audit and in-app notification commit atomically. Replays do not repeat side effects. Appointment lists, calendars and care summaries do not include command IDs or booking-origin metadata.

A known business rejection (`400`, `404` or `409`) after fresh access and command-absence checks rolls back all attempted booking effects and saves an immutable rejected command under the same writer lock. Its response is `{error,bookingOutcome:'not-created',requestId,actorId,patientId}`. An exact retry of that identity returns the same rejection even if the slot later becomes available; a freshly reviewed attempt requires a new UUID. This prevents another delayed copy of a rejected request from creating a booking after the client has been told none was created. Clients must match all marker identities before unlocking an uncertain attempt.

Schema, authorization, request-collision and unknown/internal errors have no `not-created` marker. A missing/malformed confirmation or an unmarked error cannot establish the outcome of an already uncertain request. Interactive forms retain that exact command in memory for retry; navigation/reload does not persist it. There is no command-history HTTP endpoint. Compatibility `POST /appointments` shares the freshly authorized locked creator, preserves its plain response and unknown-field stripping, and does not create UUID receipts.

## Reviewed individual appointment rescheduling

- `GET /appointments/:id/reschedule-context` → `AppointmentRescheduleContext {appointment,sourceRevision,canReschedule,blockedReason,clinicDate,bookingThroughDate}`.
- `POST /appointments/:id/reschedule-preview {doctorId,date,time,mode,expectedSourceRevision}` → `AppointmentReschedulePreview {appointmentId,sourceRevision,revision,before,after,canReschedule,blockedReason,generatedAt}` with `200`. The proposed fields remain visible for a blocked target; they are not a reserved or valid appointment until confirmed.
- `POST /appointments/:id/reschedules {doctorId,date,time,mode,expectedRevision,patientConfirmed:true,requestId}` → `AppointmentRescheduleResult {appointment,event,receipt}` with `201` new / `200` exact replay.

All three routes allow staff and the owning patient, reject unknown query/body fields and recheck current session, account, password-change state, MFA and patient access under the write lock. Mutations also revalidate CSRF. Identifiers are trimmed to 1–300 characters, date/time must be real calendar/clock values, revisions are lowercase 64-character hexadecimal strings and UUIDs are normalized to lowercase. Only future scheduled source visits qualify. The target must change the doctor, date, time or consultation mode. An unchanged target cannot silently refresh the fee or length. Existing compatibility `PATCH /appointments/:id` keeps its response and eligibility rules without gaining these review/retry guarantees.

Source revisions detect changes away and back through any appointment writer, including legacy updates, duration changes and series moves. Preview requires the displayed source revision; a conflict requires explicit source refresh. A valid preview covers current target fee/name, weekly hours, relevant time off and conflicts, clinic date/horizon and retained resource availability. Confirmation recomputes it with the current clock. Schedule-default visits adopt the target doctor's current default length; custom visits retain their recorded length. Actual moves adopt the target doctor's current fee/name. The existing same-doctor pause exception remains, while transfers to a paused doctor are blocked.

The immutable event contains `id,appointmentId,requestId,expectedRevision,before,after,patientConfirmed,createdById,createdByName,createdByRole,createdAt`. The receipt binds `requestId,actorId,patientId,appointmentId,eventId,expectedRevision`. `appointment` is the separately returned current record, which may have changed since the original event. Authorized exact retries resolve before current source, time, pause or terminal-status checks. UUID identity is unique within the rescheduling endpoint and binds the actor, appointment and complete normalized command. A collision returns `409` without an outcome marker.

Appointment updates, retained resource moves/history, immutable event/command, audit and patient activity commit atomically. A known domain `400/404/409` after fresh access and command-absence checks rolls back all attempted effects and persists a terminal rejection under the same writer lock. Its body is `{error,rescheduleOutcome:'not-applied',requestId,actorId,patientId,appointmentId}`. Every identity must match before a client unlocks an uncertain attempt. Retrying the rejected UUID always returns that rejection; a fresh review requires a new UUID. Schema, authorization, collision and unknown/internal errors have no outcome marker.

Preview/result DTOs exclude resource names, reservation details and internal reasons. Event/command IDs are not added to appointment lists, calendars or care summaries. No rescheduling-history endpoint is provided. Original booking/series origins, waitlist fulfillment, procedure associations and invoices remain unchanged. Interactive forms retain pending requests in page memory only; staff close/reopen on the same page can resume them.

## Reviewed individual appointment cancellation

- `GET /appointments/:id/cancellation-context` → `AppointmentCancellationContext {appointment,revision,canCancel,blockedReason}`.
- `POST /appointments/:id/cancellations {expectedRevision,cancellationConfirmed:true,requestId}` → `AppointmentCancellationResult {appointment,event,receipt}` with `201` new / `200` exact replay.

Staff and the owning patient can read the current context. Patients may cancel scheduled visits; staff may cancel scheduled or checked-in visits. There is no future-start or booking-horizon condition, preserving eligibility for past scheduled visits. In-consultation, completed, cancelled and no-show visits are not eligible for a new cancellation. `cancellationConfirmed` records the actor's acknowledgment of this specific cancellation; it does not claim patient consent or external contact.

Both routes reject unknown query fields and validate the path ID as a trimmed 1–300-character identifier. The command body is strict, its revision is lowercase 64-character hexadecimal, and its UUID is normalized to lowercase. Fresh account/session/password-change/MFA and patient-access checks run inside the writer transaction; writes also revalidate CSRF. The context revision binds the complete appointment, the shared monotonic appointment-change counter, retained reservation rows and latest allocation event. Appointment or allocation changes away and back invalidate an older review. Unrelated doctor fee/profile, pause, schedule or resource-maintenance changes do not block release of the recorded reservations.

The event contains `id,appointmentId,requestId,expectedRevision,before,after,cancellationConfirmed,createdById,createdByName,createdByRole,createdAt`. `after` preserves every original appointment field except `status:'cancelled'`, including absent legacy duration fields. The receipt binds `requestId,actorId,patientId,appointmentId,eventId,expectedRevision`; the separate `appointment` is the current record. Exact authorized retries return the immutable original event and receipt before current eligibility/revision checks. UUID identity is unique within this cancellation endpoint and binds the actor, appointment, operation and normalized input. A collision returns `409` with no outcome marker.

Status/counter changes, resource release and its history, cancellation event/command, audit and patient activity commit together. Known domain `400/404/409` failures after fresh access and command-absence checks roll back attempted effects and persist a terminal rejection under the same writer lock. Its body is `{error,cancellationOutcome:'not-applied',requestId,actorId,patientId,appointmentId}`. Clients must match all identities before unlocking an uncertain request. The rejected UUID can never apply later; a new reviewed attempt needs a new UUID. Schema, authorization, collision and unknown/internal errors have no definitive marker.

The context and receipt contain no resource names, reservation counts or private reasons. Cancellation metadata is not added to appointment lists, calendars or care summaries. There is no cancellation-history HTTP endpoint. Original booking/series records, fulfilled waitlist requests, procedure associations, invoices and payments are untouched, and no refund or external delivery occurs. Compatibility `PATCH /appointments/:id {status:'cancelled'}` remains available with its earlier plain response and transition rules, without these review/retry guarantees. Patient and staff forms use the reviewed route, retain uncertain requests in page memory across close/resume, and refresh the underlying list after closing a confirmed result.

## Reviewed staff appointment progression

- `GET /appointments/:id/state-context` → `AppointmentStateChangeContext {appointment,revision,actions,generatedAt,clinicDate}`. Each action contains `status,allowed,blockedReason`.
- `POST /appointments/:id/state-changes {status,expectedRevision,changeConfirmed:true,requestId}` → `AppointmentStateChangeResult {appointment,event,receipt}` with `201` new / `200` exact replay.

These routes require clinic staff. Targets are `checked-in|in-consultation|completed|no-show`: scheduled visits may be checked in or marked no-show, checked-in visits may start consultation, and in-consultation visits may complete. Only doctors and administrators may start or complete consultations; no linked-doctor requirement is added. All targets require a visit date no later than the current IST date. No-show additionally requires the scheduled start to have arrived. Other same-day actions retain their existing early-start eligibility. Repeated same-state commands with a new UUID are rejected.

Queries and commands are strict; IDs are trimmed to 1–300 characters, revisions are lowercase 64-character hexadecimal values, and UUIDs normalize to lowercase. Fresh session, active account, required password change, MFA and target-role authority are checked under the writer lock before new commands or replay. Writes revalidate CSRF. The revision covers the complete appointment, shared mutation counter, retained resource claims and latest allocation event. Changes away and back invalidate a review; unrelated doctor/profile/pause/schedule/maintenance changes do not. Context uses one captured clock, and commit checks live timing again. Clock ticks are not part of the revision.

The immutable event contains `id,appointmentId,requestId,expectedRevision,before,after,changeConfirmed,createdById,createdByName,createdByRole,createdAt`. Only status changes between its snapshots; omitted legacy duration, booked fee and recorded names are preserved. The receipt binds `requestId,actorId,patientId,appointmentId,eventId,expectedRevision,status`. The separately returned appointment is current: replaying an original check-in after completion returns that original check-in event with the completed appointment. UUIDs bind actor, appointment, target and normalized input within this endpoint; conflicting reuse returns `409` without an outcome marker.

Status/counter writes, resources/history, event/command, audit and generic patient activity commit atomically. Check-in, consultation and completion retain the recorded reservation interval; no-show releases it. Known domain `400/404/409` failures after authorization and command-absence checks roll back attempted effects, then save a terminal rejection: `{error,stateChangeOutcome:'not-applied',requestId,actorId,patientId,appointmentId}`. That UUID always returns the same rejection. All identities must match before an uncertain client attempt unlocks; a new review requires a new UUID. Schema, authorization, collision and unknown failures have no definitive marker.

The staff form requires explicit review, retains uncertain commands in page memory across Close/Resume, and guards navigation and session changes before response effects. Confirmation distinguishes the original action from later current status. Evidence stays out of ordinary patient records, calendars and summaries; no history endpoint is added. Clinical notes, procedure completion, waitlist fulfillment, billing and external delivery remain separate. Compatibility PATCH retains its previous shape and eligibility without reviewed-command guarantees.

## Reviewed weekly availability

- `GET /schedules/:doctorId/availability/history?page&pageSize` → `{items,page,pageSize,total,totalPages}`. Defaults 1/25; sizes 10, 25 or 50; page 1–1,000,000 clamps. History uses a stable newest-first timestamp/ID order and SQL-bounded materialization.

These private routes allow administrators and the doctor currently linked to the selected profile. Reception and patients are denied. The existing staff GET schedule/scheduling shapes and public slot/doctor projections remain unchanged. Reasons, history, revisions and command identities are not added to those projections or patient-facing care summaries.

`source` is `inherited` when no saved schedule row exists, otherwise `explicit`. Existing saved schedules without new events have null latestChange and no fabricated author. Revision binds doctor identity, canonical duration/sessions, source kind and latest immutable event identity. It excludes unrelated doctor metadata and timestamp-only differences. A first explicit confirmation of inherited defaults is allowed; an explicit unchanged reviewed save returns 400. Changing another doctor does not invalidate the revision; changing away and back does. New inputs reject unknown fields, trim the reason to 1–1000 characters, require a lowercase 64-character revision, normalize UUIDs to lowercase, and retain the existing strict time/duration/overlap rules with up to 70 windows.

Every read/write/retry rechecks current account, session/MFA, required password change and doctor ownership under the transaction lock. Exact retry binds actor, doctor and the complete normalized request, including the original revision; it returns the original change/receipt alongside current context before reapplying stale or booked-state guards. Reused identifiers with different intent return 409. New stale saves return 409 with the draft requiring fresh review. A fresh save also checks existing protected appointments against their full recorded interval and consultation mode. It never edits appointments or adopts the new default length for an existing visit.

A change records doctor identity/name, source `reviewed|legacy`, before/after source-and-schedule snapshots, private reason, actor display name/role and time. Receipt fields are requestId, actorId, doctorId, expectedRevision and changeId. Schedule, event, receipt and audit commit or roll back together. Both history and commands are append-only; there is no restore or deletion endpoint.

Compatibility PUT retains its full schedule input and unknown-field stripping, but now uses the same current authorization, transaction and booking guards. A first explicit write or actual value change records a legacy event with null reason. An explicit no-op returns the existing schedule/timestamp without a new event, retaining the general audit action. PUT is unversioned: explicitly submitted hours can still replace newer hours, so interactive editors should use the reviewed POST workflow.

## Retained time-off lifecycle

- `GET /time-off?doctorId&filter&page&pageSize` → `{items:[{closure,status}],page,pageSize,total,totalPages}` (staff). An optional doctor ID selects that doctor plus clinic-wide entries. Filter is `upcoming` (default), `past`, `cancelled` or `all`; upcoming/past select active entries by inclusive end date against today's IST date. Page defaults 1 and is bounded to 1–1,000,000 and clamped; size defaults 25 and accepts 10/25/50. Upcoming sorts start date/ID ascending; other views sort descending. Operational rows exclude private change notes, actors, revisions and receipts.
- `GET /time-off/:id` → `{closure,status,doctor:{id,name}|null,revision,latestChange}`.
- `GET /time-off/:id/history?page&pageSize` → `{items,page,pageSize,total,totalPages}`, with the same pagination bounds and newest timestamp/ID first.
- `POST /time-off {closure:{doctorId,startDate,endDate,startTime,endTime,reason},requestId}` creates an entry.
- `POST /time-off/:id/changes {closure:{startDate,endDate,startTime,endTime,reason},changeReason,expectedRevision,requestId}` edits an active entry.
- `POST /time-off/:id/cancel {changeReason,expectedRevision,requestId}` cancels an active entry, retaining its current/original details.

Context, history and mutations require an administrator or the doctor currently linked to that entry. Clinic-wide context/history/mutations require an administrator. The operational `reason` remains staff-readable; separate `changeReason` values are private, trimmed to 1–1000 characters and required for reviewed edits/cancellations. Creation and legacy events have null changeReason. New input objects reject unknown fields. Date ranges are inclusive; both times null mean all day, otherwise the same valid interval repeats each included date. Overnight intervals are unsupported. New create/edit requires an end date of today or later. Scope, ID and original creation time are fixed; cancelled entries are terminal and explicit unchanged edits return 400.

All three commands return `{context,change,receipt}` with 201 for a new event or 200 for exact replay. Receipt fields are requestId, actorId, operation (`create|edit|cancel`), closureId, expectedRevision (null for creation) and changeId. UUIDs normalize to lowercase. Edit/cancel revisions bind the canonical current entry, status and latest event, preventing stale writes after changes away and back without tying them to doctor-name or unrelated schedule changes. Exact replay binds actor, operation, record and normalized input, rechecks current permissions, then returns original evidence with current context before expiry/state/booking checks. Replaying an old creation after cancellation cannot reactivate the entry. Identifier collisions and stale edits return distinct 409 errors.

History retains source (`reviewed|legacy`), action (`created|edited|cancelled`), immutable before/after snapshots, actor name/role and time. Imported existing rows have no attributed event. Current records, active booking projections, events, receipts and audit writes commit atomically. Create/edit use the existing full recorded-interval booking guard, including custom visit lengths; cancellation removes only that entry's restriction. Other overlapping entries continue to block slots. No appointments, fees, weekly hours or patient-facing clinical records are rewritten.

Compatibility `POST /schedule-closures` keeps its previous response and unknown-field stripping; compatibility DELETE keeps `{ok:true}`. Both now revalidate access under the transaction lock and record actual legacy events without fabricated review notes or command IDs. Compatibility creation is still non-idempotent; interactive clients should use the reviewed endpoints. `GET /scheduling` and direct slot/series consumers continue to use active closures only.

## Custom visit durations

Staff may explicitly choose 15–240 minutes in five-minute increments. Custom start times use a five-minute grid relative to each weekly session's start. Ordinary consultations use the doctor's default duration and cadence. Both policies require the whole interval to fit one matching session and avoid doctor, patient and closure conflicts within the existing 180-day horizon. Retained resources use the same effective interval.

- `GET /visit-duration/slots?doctorId=&patientId=&date=&mode=&durationPolicy=&durationMinutes=&excludeAppointmentId=` is staff-only and returns start-time strings. Policy is `custom|schedule`; custom requires valid minutes and schedule omits them. Exclusion requires the same patient and filters retained resource conflicts. Parameters are strict, including duplicate rejection. Public `/slots` does not accept duration overrides; authorized reschedules derive policy and length from the stored appointment.
- `POST /visit-duration/bookings {patientId,doctorId,date,time,mode,reason,durationMinutes,requestId}` creates a staff-booked custom visit. It returns `VisitDurationMutation {appointment,event}` with 201; exact replay returns 200. The appointment reason follows normal booking visibility, while the separate event is staff-only. This path does not convert waitlist requests or allocate resources automatically.
- `GET /appointments/:id/duration` is staff-only and returns `VisitDurationContext {appointment,revision,scheduleDurationMinutes,currentDoctorFee,currentDoctorName,canChange,history}`. History contains immutable custom-booking and explicit duration-change events; it is not a complete history of ordinary appointment edits.
- `POST /appointments/:id/duration {durationPolicy,durationMinutes?,date,time,reason,expectedRevision,requestId}` changes a future scheduled visit and returns `VisitDurationMutation` with 200. Custom requires minutes; schedule uses the current doctor default. Date/time are required and may move together with the duration. Patient, doctor and mode remain fixed in this operation. A no-op, past source visit or non-scheduled source is rejected. The internal reason is required (1–1,000 characters) and never enters patient summaries or notifications.

The revision covers the current appointment and current doctor's schedule, fee and name. A changed source returns 409 and requires refreshed-context review. Canonical lowercase UUIDs bind actor, operation, target and normalized payload, including the revision. Exact retry occurs after authorization but before source/state/slot checks, returning the current appointment alongside its original immutable event. Reusing an ID with different intent returns 409. Original events and request receipts reject updates/deletion. Appointment changes, resource moves/resizing, evidence, audit and in-app notification commit together; any failure rolls them back.

A duration-only or policy-only change preserves the booked fee/name. An actual date/time move adopts the current doctor fee/name under the existing reschedule rule. Generic staff/patient PATCH reschedules preserve custom minutes and refresh ordinary default lengths; clients cannot supply duration fields through ordinary POST/PATCH. Status-only changes preserve duration, policy and fee. Calendar exports and patient summaries use actual recorded minutes. This feature does not rewrite procedure links, agreements, completions or invoices.

## Finite recurring appointment series

All `/appointment-series` routes require an active administrator, doctor or receptionist with a current non-temporary session. Account, session, CSRF binding and MFA state are rechecked inside the transaction. Reads are private, uncached and audited. Patients continue to use ordinary appointment APIs.

`AppointmentSeriesInput` contains `patientId`, `doctorId`, `mode`, a trimmed shared `reason` (1–300 characters), `firstDate`, `time`, `count` (integer 2–12), `intervalWeeks` (1, 2 or 4), and `durationPolicy` (`schedule|custom`). Custom policy requires `durationMinutes` (15–240 in increments of five); schedule policy forbids it. Dates and times must be real `YYYY-MM-DD` and `HH:mm` values. All fields and queries are strict.

- `POST /appointment-series/preview` with a flat `AppointmentSeriesInput` → `AppointmentSeriesPreview`. Returns normalized input, displayed patient/doctor information, current fee and duration, clinic date/horizon, every generated visit with its exact start/end dates and times, availability and generic blocking reason, `canBook`, and a revision. A date outside the 180-day horizon remains in the preview as blocked; no date is silently omitted or shifted. Generated start/end dates outside four-digit calendar years are rejected with `400`. Preview reserves nothing.
- `POST /appointment-series {input,expectedRevision,patientConfirmed:true,privateNote?,requestId}` → `AppointmentSeriesDetail`, `201` on creation or `200` for exact replay. The optional staff-only note is trimmed and limited to 1,000 characters. A canonical lowercase UUID binds the current actor and full normalized command, including the reviewed revision and confirmation. Any changed source or blocked visit returns `409`; all appointments, original series evidence, receipts, audit and patient activity commit together or not at all.
- `GET /appointment-series?q=&patientId=&doctorId=&page=&pageSize=` → `AppointmentSeriesPage`. Search is a trimmed literal ASCII-folded substring of original patient/doctor names, limited to 200 characters. Optional patient/doctor filters are exact. Page is a positive integer up to 1,000,000; page size is 10, 25 (default) or 50. Pages clamp to the last page and results sort by creation time/ID descending. List rows omit private notes and full appointment snapshots.
- `GET /appointment-series/:id` → `AppointmentSeriesDetail {series,appointments}`. Missing series returns `404`; queries are not accepted. `series` retains the original input, displayed metadata, original scheduled `bookedAppointments`, confirmation, private note and actual actor/time. `appointments` contains current members in original booking order. Later individual moves, cancellations or completion never rewrite the origin.

Preview revisions bind the displayed source, effective schedule, relevant closures/booking intervals and current clinic-date availability. The server revalidates the current clock and every slot at confirmation; the preview has no fixed reservation period. Exact authorized retries return the original series and later-current members before new-booking eligibility checks. Reusing a UUID for a different actor or payload returns `409`.

Series create ordinary appointments without series-private fields. Default-length visits follow existing individual reschedule rules; custom-length visits retain their recorded duration. Rooms, equipment, procedure plans, waitlists and invoices are unchanged. This is finite batch booking, with no recurring background scheduler. Selected-member changes use the explicit operations below.

The result includes the context fields for the selected members, normalized `appointmentIds` in original series order, `canCancel` and `revision`. Ineligible selected members remain visible and block the whole operation. Unknown or foreign members and duplicate IDs return `400`.
- `POST /appointment-series/:id/cancellations {appointmentIds,reason,expectedRevision,patientConfirmed:true,requestId}` → `{event,detail}`, `201` for a new event or `200` for an exact retry. The internal reason is trimmed to 1–1,000 characters; the revision is 64 lowercase hexadecimal characters, and the UUID is normalized to lowercase. Selection order is normalized before binding the command. A changed source, elapsed start or ineligible selection returns `409` without partial cancellation.
- `GET /appointment-series/:id/cancellations?page=1&pageSize=25` → `{items,page,pageSize,total,totalPages}`, ordered newest first. Page is 1–1,000,000 and size is 10, 25 or 50; pages clamp to the last page. Strict queries cannot broaden the series scope.

Preview revisions bind selected current appointment snapshots, displayed patient identity, reservation data and latest resource allocation events, and eligibility. They exclude generated timestamps, unrelated visits and unrelated clinician schedules. The current clock is rechecked at commit. A preview reserves nothing and is not a cancellation.

`SeriesCancellationEvent` retains `id`, `seriesId`, normalized `appointmentIds`, `reason`, `patientConfirmed:true`, `requestId`, `expectedRevision`, actual actor ID/name/role, `createdAt` and `visits:[{position,before,after,releasedReservationCount}]`. Each after snapshot differs only in `status:'cancelled'`. Event and original booking evidence are immutable. The returned `detail` is the original series plus later-current members and may advance on replay; the event always remains the original receipt. Booking and cancellation share the UUID namespace, and conflicting actor/action/series/payload reuse returns `409`.

Every selected status change, resource release and allocation history, cancellation event/receipt, audit and generic patient notice commits in one transaction. Any failure rolls them all back. Internal reasons, batch actor/receipt details and event history never enter ordinary appointments, patient summaries or notices. Existing procedure plans remain linked and can require scheduling attention; cancellation does not change agreements, clinical completion, invoices, payments or waitlists. No external cancellation message or refund is sent.

Target checks enforce current schedules, modes, cadence, closures, the 180-day horizon and full doctor/patient/resource intervals. Valid swaps and cycles are allowed; outside conflicts block the batch. Each visit retains its current doctor, mode and duration policy. The preview revision binds normalized moves, current patient and selected appointment snapshots, effective doctor/schedule settings, relevant closures and outside busy intervals, resource metadata/maintenance/claims/allocation heads, and resulting eligibility. Appointment updates, retained resource allocations and history, receipt, audit and generic patient activity commit together or all roll back. ## Upcoming appointment reminders

All routes require fresh active staff authorization with a non-temporary session; account, CSRF binding, MFA and role are rechecked inside the transaction. Patients cannot access operational reminder policies, previews, receipts or history. Reads are private, uncached and audited. Policy changes and manual runs require an administrator. Schemas are strict.

- `GET /appointment-reminder-policy` → `{policy,revision,latestChange,worker}`. Default policy is `{enabled:false,leadHours:24}`. Worker state includes automatic operation, the 300-second interval, 200-notice batch limit and last check/run/error timestamps.
- `POST /appointment-reminder-policy {enabled,leadHours,reason,expectedRevision,requestId}` → `{context,change}`, `201` new or `200` exact replay. Lead hours are an integer from 1–168; reason is trimmed to 1–1,000 characters. The change preserves before/after policy, original actor/time, reason, revision and UUID. Current context may advance after the original change.
- `GET /appointment-reminder-policy/history?page=1&pageSize=25` → a standard page of immutable policy changes.
- `GET /appointment-reminders/preview` → policy/revision, preview revision, status, generated time/window end/clinic date, batch limit, upcoming-appointment, ready, unroutable and already-recorded counts, and bounded candidate rows. Each candidate includes an episode ID, minimal appointment snapshot, exact recipient `{id,name}` and start/due timestamps. Preview reserves nothing and creates no notice. Disabled policies return no items and zero ready count, while upcoming, unroutable and already-recorded counts still describe the configured window.
- `POST /appointment-reminders/run {expectedPreviewRevision,expectedPolicyRevision,confirmed:true,requestId}` → immutable run, `201` new or `200` exact retry. A stale source, disabled policy or empty eligible batch returns `409`. New runs preserve reviewed policy/source revisions, checked time, source/actor, notice/count summaries and exact event snapshots.
- `GET /appointment-reminders/runs?page=1&pageSize=25` → paged run summaries without nested events. `GET /appointment-reminders/runs/:id` → the full immutable run and events.
- `GET /appointments/:id/reminders?page=1&pageSize=25` → current operational appointment snapshot/state and paged immutable events. State is `disabled`, `not-scheduled`, `past`, `not-due`, `no-recipient`, `recorded` or `ready`, with current episode, start/due times, recipient and recorded time where available.

All history pages use sizes 10, 25 or 50, page bounds 1–1,000,000, clamping, newest creation time/ID ordering and SQL pagination before decoding. Operational appointment snapshots contain identity/display names, date/time, mode, effective duration and status; visit reasons, fees and clinical content are excluded. Patients receive only an ordinary appointment activity item with recorded schedule details and an exact current-appointment link.

Eligibility is `now < exact IST start <= now + leadHours` and current status `scheduled`. Active patient accounts must match the appointment patient and have completed initial password rotation. Missing recipients consume no reminder identity. Deduplication is per recipient and appointment ID/date/time/doctor/mode; duration, fee, name, reason and policy edits do not resend. A changed schedule can receive a new notice, and returning to an already-reminded schedule does not duplicate it. Preview timestamps/window endpoints are excluded from revision hashing; visible source and count changes invalidate the preview, and live eligibility is checked again on confirmation.

Policy and run commands share an actor/operation/payload-bound UUID namespace. Exact replay requires current authorization but precedes current eligibility checks. Reminder evidence, receipt, audit and exact patient activity insertion are atomic. Existing appointments, clinical/billing records and care summaries remain unchanged. Automatic checks use the same service at startup and every five minutes unless `APPOINTMENT_REMINDERS_AUTO=false`, with system attribution and no empty run history. A recorded notice does not prove external delivery, reading or attendance.

## Appointment waitlist

- `GET /waitlist?status=&doctorId=` → `WaitlistEntry[]` (staff or owning patient). Optional status is `waiting | booked | cancelled | expired`. Staff can see all clinic requests and operational `patientPhone`; patients receive only their own requests without that phone field.
- `POST /waitlist {patientId?,doctorId,mode,startDate,endDate,reason}` → `WaitlistEntry` with `201`. Staff supply a patient; patient accounts use their own linkage and cannot substitute another patient. Mode is `in-person | online`; reason requires 1–300 characters. The inclusive ordered date window must be within today through 180 days ahead. A second waiting request for the same patient, doctor and mode returns `409`, even if its date window differs.
- `POST /waitlist/:id/cancel {reason?}` → `WaitlistEntry` (staff or owning patient). The optional reason has a 300-character limit. Cancelling a waiting request preserves its original record. Repeating cancellation returns the existing result and retains the first reason; booked or expired requests return `409`.

Each entry contains patient/doctor IDs and names, mode, date window, reason, creation time, derived status, nullable `appointmentId`, `closedAt` and `cancellationReason`. Expiry is derived when the end date precedes the current clinic date; no background job or expiry notification is required. Joining does not reserve a slot, prioritize urgency, offer an appointment automatically or send external messages.

Interactive fulfillment uses `POST /appointment-bookings` with `waitlistId`, explicit patient confirmation and a separate retry UUID. The appointment, terminal waitlist record, booking confirmation, audit and in-app notification commit atomically. A new command cannot fulfill an already booked, cancelled or expired request; an exact successful retry recovers its original confirmation and current appointment. Later rescheduling or cancelling the appointment preserves the request's booked history; a separate new request can be created. The compatibility `POST /appointments` path remains available without retry identity. Staff coordinate patient contact separately, and patients can choose an available slot from their own request.

## Patient records and care

- `GET /dashboard` → `Dashboard` (staff; receptionist responses exclude clinical follow-up details).
- `GET /patients?search=` → `Patient[]` (staff; receptionist responses contain demographics only).
- `POST /patients/register` accepts `{requestId,registeredByRole,name,email,phone,dob,gender,allergies,reviewedConfirmed:true}` from an administrator, doctor or receptionist. Provide each text field explicitly. Email and date of birth can be empty. Reception must send an empty allergy field. The service trims contact text, lowercases email and checks real birth dates against the clinic date.
- The first accepted request returns 201 with `{receipt:{requestId,actorId,registeredByRole,patient}}`. An exact retry from the same currently authorized account and role returns 200 with the original chart ID and role-appropriate details. Later demographic or allergy corrections appear through the current record endpoints. Reception confirmations contain an empty `allergies` field and omit `allergyStatus`. A used UUID with changed fields or a different account returns 409 after access checks. Errors do not disclose an earlier receipt.
- Each new UUID represents a separate chart, even when all demographics match. Creating a chart and its audit entry is atomic on both staff registration routes. The reviewed route also commits the private confirmation. Both routes create only the clinic chart. Portal provisioning and public signup use their own endpoints.
- `POST /patients {name,email,phone,dob,gender,allergies}` → `Patient` (staff). Walk-in records may use empty email/date of birth; reception cannot enter clinical allergies.
- `GET /patients/:id` → `PatientRecord` (clinician or owning patient; reception denied). Internal encounters are omitted from patient responses.
- `POST /patients/:id/portal-account {email,password,identityVerified:true}` → `User` (administrator). Requires an unlinked patient record and unused email; creates an active account requiring an initial-password change. Existing accounts cannot be relinked through this endpoint.
- `POST /intakes {patientId?,concern,location,duration,symptoms,triggers,previousTreatment,medications,allergies,goals,consent:true}` → `Intake` (owning patient or clinician; intake module must be enabled).
- `POST /encounters {patientId,appointmentId?,history,examination,assessment,investigations,plan}` → `Encounter` (clinician with a linked doctor profile). Notes are immutable; a linked appointment must belong to the same patient.
- `GET /care-plans` → `CarePlan[]` (clinician or owning patient), including effective follow-up status/date, revision and latest review as described below.
- `POST /care-plans {patientId,title,instructions,expectations,warnings,cost,startDate,endDate,followUpDate,medications}` → `CarePlan` (clinician with a linked doctor profile). Each medication has name, instructions, schedule, duration and warnings.
- `PATCH /care-plans/:id {status,expectedRevision?}` → hydrated `CarePlan` (clinician with a linked doctor profile); status is `active` or `completed`. A change appends a factual `source:'status-change'` event and patient notification. It does not clear unreviewed check-ins or record new clinical advice. Repeating the current status creates no additional event. An optional stale revision returns `409`.
- `POST /check-ins {carePlanId,date,adherence,feeling,note}` → `CheckIn` (owning patient, active plan, follow-up module enabled). One per plan/day, updated on repeat; dates must be within the plan and not in the future. Adherence is `taken | partial | missed`; feeling is `better | same | worse`.
- `POST /images {patientId?,caption,category,consent:true,dataUrl}` → `ClinicalImage` (owning patient or clinician; image module enabled). Category is `clinical` or `report`. Private JPEG/PNG/WebP images are limited to 5 MB and checked for a matching file signature.
- `GET /images/:id/file` → private image bytes with ownership checks.
- `GET /messages?patientId=` → `Message[]` (clinician or owning patient).
- `POST /messages {patientId?,body}` → `Message` (clinician or owning patient; follow-up module enabled). Messages have a 4,000-character limit and remain inside the platform.
- `POST /messages/send {requestId,patientId,body}` → `{receipt:{requestId,actorId,actorName,actorRole,patientId,message}}`. Both portal composers use this endpoint. Send one UUID per intention and retry with the same patient and trimmed text (1–4,000 characters). A new send returns 201. An exact retry returns 200 with the original message, including its ID, timestamp and author at send time.

The server checks current access before returning an earlier outcome. A reused UUID with a different actor, patient or text returns 409 to an otherwise authorized caller. A new command submitted while follow-up is paused receives 403 with `{code:'MESSAGE_NOT_SENT',requestId,actorId,patientId,body,message}`. This stored rejection remains final for that command after messaging resumes. Existing successes remain recoverable during the pause. An error without a matching rejection leaves the outcome uncertain.

## Reviewed daily patient check-ins

`POST /check-ins/submit` accepts `{requestId,patientId,carePlanId,date,adherence,feeling,note,expectedUpdatedAt,reviewedConfirmed:true}`. Send a UUID per reviewed submission. Use the clinic date (Asia/Kolkata), one of `taken | partial | missed` for adherence and one of `better | same | worse` for feeling. The note is required and may be empty. For the first report on a plan/date send `expectedUpdatedAt:null`. For a correction send the exact `createdAt` of the current report the patient reviewed. A new report or correction requires an active plan, enabled follow-up and a date inside the original treatment period through the current clinic day.

A successful new command returns 201 with `{receipt:{requestId,actorId,patientId,carePlanId,date,expectedUpdatedAt,operation,checkIn}}`. The operation is `created` or `corrected`. A correction retains the report ID and advances its version timestamp. The same currently authorized patient can retry the exact command for 200 and the original report, even after later corrections, completion or a module pause. Retrieve the patient's record for the current report. The compatibility route `POST /check-ins` still returns a plain check-in, with 201 on creation and 200 on replacement.

For an authorized new command, a paused module returns 403, a completed plan or a changed source version returns 409, and an ineligible report date returns 400. These outcomes carry `{code:'CHECK_IN_NOT_SAVED',actorId,command,message}` and repeat on exact retry. The returned command contains the reviewed values after normalization. Match it to the pending attempt before starting a new review. Authorization errors, malformed input and UUID collisions carry no such proof.

## Reviewed care-plan creation

`POST /care-plans/create` accepts a flat object with `requestId` (UUID), `patientId`, `doctorId` (the professional profile reviewed), `reviewedConfirmed:true`, `title`, `instructions`, `expectations`, `warnings`, `cost`, `startDate`, `endDate`, `followUpDate` and `medications`. All fields are required. The medication array accepts zero to 30 ordered items, each with `name`, `instructions`, `schedule`, `duration` and `warnings`. Empty strings are accepted for expectations, warnings and cost. Dates are real calendar dates in YYYY-MM-DD format. The end and follow-up dates must each fall on or after the start date.

A new save returns 201 with `{receipt:{requestId,actorId,patientId,doctorId,plan}}`. An exact retry returns 200 with that original active plan, including the original names and creation timestamp. Current status, ownership and follow-up reviews remain available through the existing read endpoints. Pausing follow-up leaves care-plan creation available.

Both new and repeated requests require current patient access and a doctor or administrator account linked to a professional profile. A different actor, reviewed professional, patient or normalized payload reusing the request ID receives an unmarked 409 after authorization. If a new request names a different professional from the account's current doctor, the clinic records a 409 with `{code:'CARE_PLAN_NOT_CREATED',actorId,command,message}`. The returned command contains the normalized reviewed values. A matching rejection lets the clinician review the draft again. Other errors leave the original outcome unresolved. The legacy `POST /care-plans` continues to return the plain saved plan.

## Reviewed intake submission

`POST /intakes/submit` accepts a flat object with `requestId` (UUID), `patientId`, `concern`, `location`, `duration`, `symptoms`, `triggers`, `previousTreatment`, `medications`, `allergies`, `goals` and `consent:true`. All text is trimmed. Concern, location and duration each require 1–300 characters. The other six answers allow empty strings and up to 8,000 characters each. The portal uses this endpoint. A new save returns 201 with `{receipt:{requestId,actorId,patientId,intake}}`. An exact replay by a currently authorized submitter returns 200 and the original saved intake, even while new intake is paused.

An otherwise authorized attempt to reuse the UUID with different answers, actor or patient returns 409. A new submission during a pause returns 403 with `{code:'INTAKE_NOT_SUBMITTED',requestId,actorId,patientId,answers,message}`. Here `answers` contains all nine normalized strings and the original consent. This rejection is durable across module resumption. A client that receives an incomplete response can retry the original request. It can start a new attempt after validating a matching rejection and obtaining fresh agreement.

## Reviewed consultation documentation

- `POST /consultation-notes {patientId,appointmentId?,history?,examination?,assessment,investigations?,plan,reviewedConfirmed:true,requestId}` records an original note.
- `POST /encounters/:id/amendment-recordings {reason,text,reviewedConfirmed:true,requestId}` appends a correction or clarification to an original note.

Both return `ConsultationRecordingResult {encounter,amendment,receipt}`, with `201` for a new recording and `200` for an exact replay. `amendment` is null for note creation; otherwise it is the original saved amendment. The receipt contains `requestId,actorId,operation:create|amend,patientId,encounterId,amendmentId:null|string,doctorId`. The receipt's doctor is the author of this operation, so an amendment may have a different author from its original note. Later amendments, appointment changes and author profile changes do not alter an earlier result.

New routes reject unknown query/body fields. IDs trim to 1–300 characters; clinical text trims to at most 8,000 characters. Assessment and plan are required, while history, examination and investigations default blank. Amendment reason and text are required. Request UUIDs normalize to lowercase. The acknowledgment means the author reviewed this submitted content; it does not assert patient consent or clinical approval by someone else.

Current session, expiry, CSRF, active account, required password rotation, MFA, doctor/administrator role, valid linked doctor profile and patient access are checked inside the writer transaction before recording or replay. A linked clinician may document any clinic patient or amend another clinician's note. Optional appointment linkage requires only the same patient; there is no new date, status or assigned-doctor condition. These are additive records, so no optimistic version or clinical-source review claim is introduced.

A shared append-only command registry binds the UUID to the actor, operation, patient, source encounter and digest of all normalized input. It stores receipts or terminal rejections without copying clinical text into command metadata. Conflicting reuse returns `409` without an outcome marker. Note/amendment insertion, receipt and audit commit atomically. Legacy `POST /encounters` and `POST /encounters/:id/amendments` use the same fresh authorized atomic writers while preserving plain `201` responses, field stripping and absence of a UUID guarantee.

Known domain `400/404/409` errors after source authorization and command-absence checks roll back attempted effects before saving `{error,consultationOutcome:'not-recorded',requestId,actorId,operation,patientId,encounterId}`. The encounter ID is null for creation or the source ID for amendment. An exact rejected request stays rejected even if its appointment link later becomes valid. A fresh reviewed attempt needs a new UUID. Missing private patients/encounters, authentication, clinician-link, schema, collision and unknown failures have no definitive marker. Clients match every marker identity before unlocking an uncertain request.

Original notes and amendments remain immutable and clinician-only. They do not appear in patient/reception/public projections or patient-facing summaries, do not create notifications, and do not change appointments or care plans. No command-history endpoint is added. The shared staff form reviews exact text, locks uncertain submissions, supports Close/Resume within the current record, validates saved identities/content and guards navigation before response effects. Pending clinical text stays in page memory only.

## Follow-up review and worklist

- `GET /follow-up-worklist?scope=mine|all` → `FollowUpWorkItem[]` (doctor/administrator). Defaults to `mine` for doctors and `all` for administrators. Ownership starts with the original care-plan doctor and follows the latest assignment; `all` uses the existing clinic-wide clinical permissions. Includes active and completed plans, sorted by due status, unreviewed count, next review date and patient name. Each item contains `carePlan`, `patient`, `ownerDoctorId`, `ownerDoctorName`, `revision`, `latestReview`, `unreviewedCheckIns`, `unreviewedCount` and `due`.
- `GET /care-plans/:id/reviews` → newest-first `FollowUpReview[]` (clinician) or `PatientFollowUpReview[]` (owning patient). Reception is denied. Patient responses omit internal `assessment` and `checkInSnapshots`.
- `POST /care-plans/:id/reviews {expectedRevision,assessment,patientInstructions,disposition,nextReviewDate?}` → hydrated `CarePlan` with `201` (linked clinician; follow-up module enabled). Assessment and patient instructions are required, with an 8,000-character limit each. Disposition is `continue | visit-requested | complete`. Continuing or requesting a visit requires today's date or a future `nextReviewDate`; completion stores `null`. `expectedRevision` must match the current 64-character revision from the plan/worklist. A new review, assignment or new/edited check-in makes an earlier revision stale and returns `409` without saving.
- `GET /follow-up-owners` → `FollowUpOwner[]` (doctor/administrator): `doctorId`, `doctorName` and `activeAccounts`. Eligible profiles have at least one active linked doctor/administrator account; an account still requiring its initial password change counts as active.
- `GET /care-plans/:id/assignments` → newest-first `FollowUpAssignment[]` (doctor/administrator; patients and reception denied). Each event records the previous/new doctor IDs and names, reason, assigning account ID/name and creation time.
- `POST /care-plans/:id/assignment {doctorId,reason,expectedRevision}` → hydrated `CarePlan` with `201`. Administrators, including those without a doctor profile, can reassign; a doctor must be the current follow-up owner. The handover reason requires 1–8,000 characters and the current 64-character revision is mandatory. An ineligible target returns `400`; the current owner as target or a stale revision returns `409`.

The clinician composer uses two plan-scoped endpoints. Both require current patient access and an active doctor or administrator account linked to a clinical profile.

- `GET /care-plans/:id/review-context` returns `{item,checkInSnapshots,doctorId,doctorName,followUpEnabled,latestAssignmentId}`. The worklist item, its revision and the complete set of current report versions describe one database snapshot. The latest handover ID is null before the first assignment. Together with the report fingerprints and latest review ID, it lets the client verify the revision. This context remains readable during a follow-up pause.
- `POST /care-plans/:id/reviews/record` accepts `{requestId,patientId,carePlanId,doctorId,expectedRevision,assessment,patientInstructions,disposition,nextReviewDate,reviewedConfirmed:true}`. Send a fresh UUID for each deliberately reviewed submission. Use the clinician profile and revision from the context, with the same disposition and text limits as the compatible review endpoint. Use an explicit null date for completion. A new save returns 201 with `{receipt:{requestId,actorId,patientId,carePlanId,doctorId,expectedRevision,review}}`. An exact retry by the same currently authorized account returns 200 with the original review, including its author and the report versions seen at save time.

An exact retry remains recoverable after another review, handover, report correction, elapsed review date or module pause. For a new command the server records a refusal when the revision or reviewed clinician has changed (409), follow-up is paused (403), or the next review date has passed (400). The body is `{code:'FOLLOW_UP_REVIEW_NOT_RECORDED',actorId,command,message}` with normalized fields. Match this complete response to a pending submission before reviewing a fresh attempt. Malformed input, authorization errors, mismatched targets and UUID collisions provide no such confirmation.

Assignment changes the worklist owner and routing for subsequent check-in notifications, preserving original plan/review authorship. Assignment history and reasons remain clinician-only; patient hydration includes only an opaque changed revision. Reassignment records an immutable event, audit and generic new-owner notification together. It does not clear unreviewed reports or revise treatment. Operational reassignment remains available when the follow-up module is paused.

Hydrated care plans in plan lists, patient records and dashboard follow-ups include `effectiveStatus`, `effectiveFollowUpDate`, `followUpRevision` and `latestReview`. Their original `startDate`, `endDate` and `followUpDate` remain unchanged. A plan is due when active and its effective review date is today or earlier. The latest event determines active/completed status and the next review date; completed plans have no effective review date. Patient-facing hydration applies the same internal-field filtering as review history.

Each immutable `FollowUpReview` records its ID, plan, linked doctor/name, `source` (`clinical-review | status-change`), assessment, patient instructions, disposition, next review date, timestamp and full check-in snapshots. Each snapshot carries the check-in `id`, `updatedAt`, SHA-256 `contentHash` and original `snapshot`. The snapshot timestamp reflects the check-in's latest stored submission time, including a same-day replacement. The server captures these fields; clients cannot provide or replace them. Current versions not captured by the latest clinical review remain unreviewed. Editing a previously reviewed check-in reopens that work while preserving the exact evidence previously reviewed.

Completing a plan stops check-ins. Continuing follow-up does not extend the original treatment dates or medication duration; `visit-requested` does not book an appointment. A status-only change can reopen a plan but does not count as clinical review. Existing history and the status-only endpoint remain available when the follow-up module is disabled. Check-ins describe patient reports; review queues and dispositions do not diagnose, triage urgency or generate treatment advice.

## Follow-up escalation

Types are in `shared/follow-up-escalation.ts`. All routes reject unknown input/query fields, require a normal authorized session, and return `Cache-Control: no-store`.

- `GET /follow-up-escalation-policy` → `EscalationPolicyContext` (doctor/administrator): current policy/revision, newest-first policy history, follow-up module state and actual local worker state. Default policy: `{enabled:false,ownerAfterDays:3,clinicAfterDays:7}`; initial history is empty.
- `POST /follow-up-escalation-policy {enabled,ownerAfterDays,clinicAfterDays,reason,expectedRevision,requestId}` → `EscalationPolicyMutation` with `200` (administrator). Owner threshold is an integer 1–30; clinic threshold must exceed it and be at most 90. Reason is trimmed, 1–1,000 characters. A no-op is `400`; a stale revision is `409`. A canonical UUID is bound to the actor and normalized command. Exact replay returns the original change with the current context, including after later policy changes.
- `GET /follow-up-escalations/preview` → `EscalationPreview` (administrator). Contains clinic date, policy/revisions, `ready | disabled | paused` status, full ready/unroutable/already-notified counts and up to 200 ready candidates, oldest review date/plan ID first. Candidates preserve plan/patient/owner identity, source review/assignment IDs, episode, overdue days, stage, routing and exact recipient account snapshots. Disabled/paused policies can show hypothetical candidates but cannot create notices. Reading never sends.
- `POST /follow-up-escalations/run {expectedPreviewRevision,expectedPolicyRevision,requestId}` → `EscalationRun` with `200` (administrator). Recomputes the preview transactionally and rejects stale source/recipient/date/policy/module state with `409`. Disabled or paused policies also return `409`. Actor-bound exact replay returns the original run before checking newer source state. A new zero-notice check can return a receipt with zero counts. Events, exact-recipient activity, receipt and audit commit together.
- `GET /care-plans/:id/escalations` → `EscalationHistory` (doctor/administrator). Exact plan identity, current operational state and newest-first immutable events across review episodes, including completed plans. Patient/reception access is denied. Reading history does not resolve the plan or mark activity read.

Overdue days are Asia/Kolkata calendar days after the effective review date; the date itself is zero. Completed plans and plans without a reached threshold are ineligible. An episode binds plan ID, latest review/status-change ID and effective review date. A recorded clinic-stage notice suppresses future owner-stage notices for that episode; an owner notice can be followed by a later clinic notice. A plan already at the clinic threshold receives only that stage. Check-ins, assignments and policy edits do not reset dedupe.

Owner routing targets active linked clinician accounts for the current owner, falling back to eligible clinic clinicians when unavailable. Clinic routing targets all eligible clinical accounts. Inactive accounts, accounts still requiring their initial password change and missing/invalid clinician links are excluded. No eligible recipients means no event or consumed dedupe key, allowing a later retry. Recorded recipient snapshots do not imply read state or external delivery. Only the clinical worklist receives operational `escalation` state; these fields never enter patient care-plan hydration or summaries, and notices/policy edits do not change clinical review revisions.

The server runner uses the same service at startup and every 900 seconds unless `FOLLOW_UP_ESCALATION_AUTO=false`. Automatic receipts use `source:'automatic'`, null request/actor IDs and `createdByName:'Follow-up scheduler'`; no-notice polls only update bounded heartbeat metadata. API app construction alone does not start it. Events use the existing `follow-up` activity kind and an exact-plan `/clinic/follow-ups?escalation=...` link.

## In-app activity

- `GET /activity?unread=true|false&limit=&cursor=` → `ActivityFeed` (`items`, `unreadCount`, `nextCursor`). Limit defaults to 30, with a range of 1–100. `unread=true` filters the page; `false` or omission includes read and unread items. The count covers all currently unread items for the recipient, not just the page. Items are newest first. Pass the previous `nextCursor` to load older items; a cursor outside the account's permitted feed returns `400`.
- `POST /activity/:id/read {}` → `ActivityItem`. Only the recipient can mark an item read; an inaccessible item returns `404`. Repeated reads preserve the initial `readAt`.
- `POST /activity/read-all {throughId}` → `{markedRead:number}`. Marks all unread items for the recipient at or before the supplied feed item, including older pages not yet loaded. Use the newest item from the displayed snapshot. Items arriving after that snapshot stay unread; an inaccessible snapshot ID returns `404`.

An `ActivityItem` has `id`, `kind`, `title`, `detail`, `href`, `createdAt` and nullable `readAt`. Kinds are `appointment`, `care-plan`, `message`, `check-in`, `investigation`, `procedure`, `follow-up`, `waitlist`, `billing` and `image-annotation`. Waitlist creation/cancellation/booking, follow-up handover, invoice creation, recorded payments and billing corrections generate supported in-app events. A waitlist booking sends one request-specific booking notification, without duplicating the ordinary appointment-created notification. Event contents are immutable; read state is separate. Listing a feed never marks it read, and reading a notification does not mark clinical information reviewed or complete a task.

Feeds are account-specific. Patients see only their own patient notifications; doctors and administrators see their own clinical notifications; reception receives an empty feed. Current account permissions still apply after role changes. Clinical events with an assigned doctor route to active linked accounts for that doctor, falling back to the active clinical team only when no owner account is active. The author is excluded after recipient selection. Patient messages without a specific owner notify the active clinical team. No notification exposes internal assessments, unpublished interpretations or private message text.

Notifications are recorded with the source event in one transaction and deduplicated by recipient/event key. Events notify accounts active at that moment; creating or reactivating an account does not backfill earlier events. These are in-app updates only: no email, SMS, push delivery or emergency monitoring is configured. Enabled follow-up escalation policies can create scheduled in-app notices for overdue review dates.

## Image annotations and patient-facing summaries

- `GET /images/:id/annotations` → `ImageAnnotationHistory` (`imageId`, `revision`, `versions`). Clinical staff receive all revisions with a SHA-256 optimistic revision token. Owning patients receive published revisions only and `revision:null`; no private revision IDs, notes or counts are exposed. Reception is denied. Versions are newest first.
- `POST /images/:id/annotations {expectedRevision,note,markers}` → updated history with `201` (linked clinician). A nonempty note or at least one marker is required. Notes allow up to 4,000 characters; at most 50 markers are accepted. New versions are always private, retain clinical authorship/date and the original image fingerprint, and never change image bytes. The current revision is checked transactionally; stale saves return `409`.
- `POST /images/:id/annotations/:versionId/publish {expectedRevision,patientSharingConfirmed:true}` → updated history (linked clinician). Newly sharing requires the current revision and latest saved version. Repeating a previously completed publication preserves its original timestamp and notification. Explicit publication, audit and a generic patient activity entry save in one transaction. There is no edit/delete/unpublish endpoint.

Each marker has a unique UUID `id`, a color from `red | amber | green | blue | purple | white`, and an optional label up to 200 characters. Rectangle/ellipse markers have `type`, `x`, `y`, `width`, `height`; arrow markers have `type:'arrow'`, `x1`, `y1`, `x2`, `y2`. All coordinates are image-relative values from 0 to 1, rounded to six decimal places. Box dimensions must stay positive and entirely within the image. Arrow endpoints must differ. Arbitrary geometry fields, SVG markup, colors and client-authored provenance are rejected. Coordinates describe position, not physical measurements or automated clinical interpretation.

The image module must be enabled to save or publish. Existing history remains readable while paused. Original image rows, annotation versions and publication events are immutable. New image uploads record authenticated uploader metadata, byte count and SHA-256; legacy uploads retain absent provenance rather than fabricated authorship. Upload plus audit is transactional.

- `GET /patients/:id/care-summary` → `CareSummary` (`schemaVersion:1`, `audience:'patient'`, `generatedAt`, `timezone:'Asia/Kolkata'`, `revision`, clinic contact, patient, appointments, intakes, care plans with patient-facing review history, check-ins, investigations, procedures, image metadata/published annotations, PDF metadata, invoices and safe `invoiceHistories`). Patients may access only their own summary; clinical staff may access the clinic's patients. Reception is denied. Both eligible role groups receive the same patient-facing projection.
- `GET /patients/:id/care-summary/download?revision=` → private JSON attachment. The required 64-character revision must match the current patient-visible content; stale requests return `409` and require a refresh. The export can have a later generation timestamp but must have the same content revision. Filename uses an opaque identifier rather than the patient's name. Responses use no-store and nosniff headers, with authorization and audit on every request.

Summaries exclude internal encounters/amendments, private messages, clinician follow-up assessments/report snapshots/assignment reasons, unpublished investigation interpretations, private image annotations and original file bytes. Attachment URLs remain private authenticated routes. Private drafts and operational handovers do not invalidate a summary unless patient-visible content actually changes. Original regimen dates and instructions remain distinct from later shared follow-up reviews. Printing keeps the displayed snapshot; this is a patient-facing summary rather than a complete internal clinical-record release.

### Saved care-summary copies

- `POST /patients/:id/care-summary/copies {expectedRevision,requestId}` → `{copy,receipt}`, `201` for a new copy and `200` for an exact retry. `expectedRevision` is the displayed summary's 64-character lowercase content revision; `requestId` is a UUID, normalized to lowercase. No client-authored summary, author, label or timestamp is accepted. A changed shared record returns `409`; a serialized copy above 10 MiB returns `413` without saving or truncating it.
- `GET /patients/:id/care-summary/copies?page=1&pageSize=25` → `{items,page,pageSize,total,totalPages}`. Pages are bounded to 1–1,000,000 and sizes to 10, 25 or 50. Items contain metadata only, ordered by saved date and ID descending. Unknown or repeated query fields are rejected.
- `GET /patients/:id/care-summary/copies/:copyId` → `{copy,summary}`. `summary` is the original immutable `CareSummary`; it is not rebuilt from the current record.
- `GET /patients/:id/care-summary/copies/:copyId/download` → the exact stored UTF-8 JSON attachment, including its original generation timestamp. No live revision is required. It remains protected by current authorization and no-store headers.

`copy` contains `id`, `patientId`, `patientName` (as recorded in this copy), `sourceRevision`, `generatedAt`, `savedAt`, `savedBy:{name,role}`, `contentSha256` and `byteLength`. The fingerprint covers the exact download bytes; it is not a digital signature. The save-only `receipt` contains `requestId`, `actorId`, `patientId`, `expectedRevision` and `copyId`. Receipts bind the UUID to the original actor, patient and payload; a conflicting reuse returns `409`. Exact retries return the original result even after the live record changes.

Owning patients, doctors and administrators can save and read copies; reception is denied. Every operation rechecks the current account, session, MFA and patient access inside its transaction. A save commits the server-generated snapshot, receipt and audit together. Copies and receipts cannot be edited or deleted through this feature. Saving records preservation, not clinical approval, a complete record release or an external delivery. Attachment bytes are not duplicated; file links still require current access. Historical copies may retain content that has since changed or stopped being shared.

### Saved-copy attachment bundles

Base: `/patients/:id/care-summary/copies/:copyId/bundle`. Every endpoint applies the existing patient-owned or clinical saved-copy permissions; reception is excluded. Current account, session, initial-password and MFA state are checked again under the transaction lock. Paused modules preserve this read/export access.

- `GET /attachments?page&pageSize` → `{copy,items,page,pageSize,total,totalPages,limits}`. Defaults 1/25; page sizes 10, 25 or 50; pages 1–1,000,000 clamp to the current total. Only frozen copy references appear, ordered by type/id. A bounded page checks same-patient BLOB existence/length without fetching file bytes. Availability is `present`, `missing`, `unsupported` or `too-large`; presence alone does not establish integrity.
- `POST /preview {attachments:[{type:'document'|'image',id}]}` → `{copy,selection,manifest,revision,filename,byteLength,contentSha256,limits}`. Select 1–20 unique references. The response canonicalizes selection order, verifies saved JSON and every selected original, and calculates the exact complete ZIP size and SHA-256.
- `POST /download {attachments,expectedRevision}` → exact ZIP bytes after revalidation. Response headers include attachment disposition, `application/zip`, `Content-Length`, `X-Content-SHA256`, `X-Bundle-Revision`, no-store, nosniff and a sandbox CSP. Revision is a lowercase 64-character SHA-256 value binding the canonical manifest. There is no conditional 304 response.

Limits are 5 MiB per selected original and 25 MiB for the whole ZIP, including the saved JSON, manifest and ZIP metadata. Empty, duplicate, foreign or unreferenced selections return 400; missing, invalid, mismatched or stale selected content returns 409; oversize packages return 413. Queries and bodies reject unknown fields. All validation and download audit commit before attachment headers are sent; an audit failure returns no archive.

The archive contains `care-summary.json` with the exact stored bytes, `manifest.json`, and selected originals under generated `attachments/` paths. User labels and filenames never become archive paths. The version-one manifest records the frozen copy and summary hash, file labels/MIME/size/hash/upload attribution and verification kind. Files with a saved hash use `saved-sha256`; legacy images lacking one use `computed-at-export`, which does not prove historical byte identity. PDF reports require their saved fingerprint. Original images are not rasterized with overlays; shared annotations remain in the saved JSON. No current-only files or private clinical fields are added, and referenced URLs are never fetched. Repeating the same copy/selection with unchanged originals produces identical bytes, independent of selection order or requesting account. Bundles are generated on demand and not persisted; ordinary JSON download remains available.

## Retrying a private upload

The patient and clinic portals use `POST /images/upload` for photographs and report images and `POST /documents/upload` for PDF reports. Supply `requestId` (UUID), `patientId`, `consent:true`, the base64 `dataUrl` and `sha256` (64 lowercase hexadecimal digits computed over the decoded original bytes). Images also require `caption` and `category` (`clinical` or `report`). PDFs require `title` and `originalName`. Both enforce the existing format and five-megabyte limits.

A first save returns 201 with `{receipt:{requestId,actorId,patientId,kind,file}}`. The kind is `image` or `document`, and `file` contains the original metadata, including the private download URL, uploader, size, fingerprint and creation date. An authorized exact retry returns 200 with the same receipt. A new request ID permits a deliberate second upload of the same file. Reusing an ID for another upload, patient, actor, file type or accepted metadata returns 409 to an otherwise authorized caller.

Image capture can be paused independently of PDF uploads. An authorized retry of a successful image upload still returns its original receipt during a pause. A valid new image upload during the pause receives a durable 403 with `{code:'UPLOAD_NOT_SAVED',requestId,actorId,patientId,kind:'image',sha256,caption,category,mimeType,sizeBytes,consent:true,message}`. Replaying it after resumption returns the same rejection. The portal matches the complete outcome before allowing a new attempt. Authentication errors, collisions and interrupted responses leave a pending request unresolved. The existing `POST /images` and `POST /documents` endpoints continue returning plain file metadata.

## Private PDF reports

- `GET /documents?patientId=` → `PatientDocument[]` (doctor/administrator or owning patient; reception denied). Patient accounts default to their own record; clinical staff supply `patientId`.
- `POST /documents {patientId?,title,originalName,dataUrl,consent:true}` → `PatientDocument` with `201`. Accepts canonical base64 `application/pdf` data URLs, up to 5 MB decoded, inside the existing 7 MB JSON request limit. Title and original filename have a 200-character limit. Filenames must end in `.pdf` and contain no path separators or control characters. The server validates PDF header/end markers and records the authenticated uploader, byte count and SHA-256 fingerprint.
- `GET /documents/:id/file` → authorized PDF attachment. The server uses a generated download filename, `Content-Disposition: attachment`, `Content-Security-Policy: sandbox; default-src 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`.

`PatientDocument` contains `id`, `patientId`, `title`, `originalName`, `mimeType:'application/pdf'`, `sizeBytes`, `sha256`, `createdById`, `createdByName`, `createdByRole`, `createdAt`, `url` and `consent:true`. List responses contain metadata, not file bytes. Document metadata and original bytes are immutable; there is no edit/delete endpoint. PDFs use separate storage and routes from the raster image library.

These checks recognize a candidate PDF; they do not sanitize or malware-scan it. Original files are downloaded rather than embedded. The fingerprint identifies the uploaded bytes, not their issuing laboratory or medical accuracy. Upload agreement records private care use and does not authorize public publication.

## Investigations, procedure records and amendments

`GET /patients/:id/clinical-workflows` → `PatientClinicalWorkflows` with `investigations`, `procedures` and `amendments` arrays. Doctors and administrators may inspect the clinic's records; patients receive only their own. Reception is denied. Patient responses contain no internal encounter amendments and omit every unpublished investigation-review object. Top-level arrays are newest first; nested results, reviews and procedure agreements are chronological, so the last entry is the latest.

All clinical authorship below requires an account linked to a doctor profile, including administrators. An unlinked administrator can inspect authorized records but cannot create orders, clinical interpretations, amendments or procedure records. Names, identifiers, roles and timestamps are derived by the server.

### Investigation orders and review

- `POST /investigations {patientId,title,kind,reason,instructions,dueDate?}` → `Investigation` with `201` (linked clinician). Kind is `laboratory | pathology | imaging | other`. Reason and patient-facing instructions are required; optional due date may be `null` or today/a future date. The original order is immutable.
- `POST /investigations/:id/results {note?,documentIds?}` → updated `Investigation` with `201` (owning patient or linked clinician). Requires a note or at least one PDF-report ID. The 0–10 document IDs must be unique and belong to the same patient. Each submission is an immutable `InvestigationResult` with authenticated `submittedById`, name, role and timestamp. Notes and raw reports are patient-visible and remain distinct from clinician interpretation.
- `POST /investigations/:id/reviews {resultId,summary,followUp?,publishToPatient?,expectedRevision?,requestId?}` → updated `Investigation` with `201` (linked clinician). The selected result must be the latest submission; a stale selection returns `409`. Summary is required. Publication defaults to `false`; explicit `publishToPatient:true` shares the interpretation. Review text is immutable; subsequent reviews are additional entries.
- `POST /investigations/:id/reviews/:reviewId/publish {}` → updated `Investigation` (linked clinician). Explicitly shares an existing interpretation without changing its content. Repeating the publication preserves its original publication timestamp. New publication on a cancelled investigation returns `409`, while an already published review remains idempotently readable through this action.
- `POST /investigations/:id/cancel {reason}` → updated `Investigation` (linked clinician). Cancellation preserves history and prevents new results/reviews. A cancelled order or an investigation whose latest result is already reviewed returns `409`.

Investigation status is derived: `ordered` before a result, `result-received` when the latest submission has no review, `reviewed` after a clinician reviews that latest submission, or `cancelled`. A supplemental submission returns the order to `result-received` and retains earlier results and interpretations. A reviewed result may still have no patient-visible interpretation until explicit publication. The application does not classify a result as normal/abnormal or generate a diagnosis.

The patient and clinician result forms use `POST /investigations/:id/results/submit` with `{requestId,patientId,investigationId,submittedByRole,note,documentIds,reviewedConfirmed:true}`. The role must match the current account (`patient`, `doctor` or `admin`), the path and body must identify the same investigation, and a clinician needs a linked professional profile. Send a trimmed note of up to 8,000 characters, up to ten distinct same-patient PDF document IDs in the reviewed order, or both. An empty note is valid when at least one PDF is selected. Use a new UUID for each intentional submission, including supplemental results with the same contents.

A new save returns 201 with `{receipt:{requestId,actorId,patientId,investigationId,result}}`. An exact retry by the same currently authorized account and role returns 200 with the original result, author, time and ordered links. Subsequent review, publication, cancellation, reassignment and supplemental results leave that confirmation recoverable. Use the role-filtered clinical workflow read to see the current investigation. The compatible `POST /investigations/:id/results` continues to append on each call and return the updated investigation with 201.

For an otherwise authorized new command, a cancelled investigation returns 409. A missing document or a document outside this patient’s record returns 400 with the same generic explanation. Both refusals are recorded with `{code:'INVESTIGATION_RESULT_NOT_SUBMITTED',actorId,command,message}` and repeat on exact retry. Match the returned normalized command to the submitted one before starting a new attempt. A malformed command, lack of access or conflicting use of a UUID supplies no such confirmation.

### Investigation worklist and responsibility

All endpoints here require an active doctor or administrator account. Patients and reception are denied. Queue reads remain available while optional modules are paused.

- `GET /investigation-worklist?scope=mine|all` → `InvestigationWorkItem[]`. Defaults to `mine` for doctors and `all` for administrators. Includes all statuses, original ordering identity, current patient display name, current owner and `ownerAvailable`, original requested date, latest result/review IDs and dates, `needsReview`, `awaitingPublication`, `pastRequestedDate` and current revision. It omits result/review free text and assignment reasons. A doctor may inspect all clinic work; ownership is not an access boundary.
- `GET /investigation-owners` → `{doctorId,doctorName,activeAccounts}[]`, containing only clinician profiles with at least one active linked doctor/administrator account.
- `GET /investigations/:id/review-context` → `InvestigationReviewContext`, extending the work item with the full clinical `investigation` and newest-first `assignments`. Reads are audited and do not change review or activity state.
- `POST /investigations/:id/assignment {doctorId,reason,expectedRevision,requestId}` → current review context, `201` for a new assignment and `200` for exact replay. Only the current responsible doctor or an administrator may create a handover. Destination must have an active linked clinical account. Reason is trimmed 1–1,000 characters; UUID and current 64-hex revision are required. Assigning the same owner or a cancelled investigation returns `409`.

Assignment events retain previous/new doctor identity, private reason, actual recording account and timestamp. Existing investigations default to the original ordering clinician without fabricated assignment events. Source order, requested date and clinical authorship remain unchanged. Patient workflows and care summaries receive no assignment records, internal reasons or revisions; private handovers do not invalidate a patient-visible summary revision.

For review creation, `expectedRevision` and UUID `requestId` must be supplied together or both omitted for legacy callers. Current application forms always provide both. The revision covers results, reviews, publications, cancellation and assignment history. Changed source state returns `409`; an exact actor-bound retry returns the current clinical investigation with `200` without another review, even if later source changes occurred. Legacy callers retain the existing latest-result check but have no full-context concurrency or command replay guarantee. Multiple intentional reviews of the latest result remain supported after loading current context.

Review and assignment commands share an actor/operation/investigation/payload-bound UUID namespace. Expected revision is excluded from replay intent; mismatched reuse conflicts. Assignment replay checks precede current-owner checks so an original owner can safely confirm a completed handover. Source event, command receipt, audit and any notification commit atomically. New-result activity routes to the current owner and links to the exact submitted result; if no linked owner account is active, eligible clinical accounts receive the event using the existing fallback rules. Free-text handover reasons never enter notifications.

`needsReview` means the latest result has no review and the order is not cancelled. `awaitingPublication` means the most recent review of the latest result remains private on an uncancelled order. `pastRequestedDate` applies only to orders without a result whose original due date is earlier than today in Asia/Kolkata. It is not a review deadline, clinical severity score or urgency classification.

### Consultation amendments

- `POST /encounters/:id/amendments {reason,text}` → `EncounterAmendment` with `201` (linked clinician). Both fields are required. The server derives the patient from the original encounter and records the amending doctor and timestamp. The original consultation note remains unchanged. Amendments are returned only in the clinician's workflow view and cannot be edited or deleted.

### Procedure catalogue

Types are in `shared/procedure-catalogue.ts`. Catalogue reads are private to doctors and administrators. Creating versions and publishing requires a linked clinician; archive/reactivation requires an administrator. Patients and reception cannot read catalogue content or history. No patient indication, appointment, decision or outcome is stored in a template.

- `GET /procedure-catalogue?search=&active=&publication=&page=&pageSize=` → `ProcedureCataloguePage`. Active is `true|false|all` (default `true`); publication is `all|published|unpublished` (default `all`). Search is a literal substring of latest/published titles, up to 300 characters. Page sizes are 10/25/50, default 25; pages clamp to the current result set. Publication and active filters are independent.
- `GET /procedure-catalogue/:id` → `ProcedureTemplateDetail`: current row, latest version, current published version and its publication event (or null), latest 25 lifecycle events and total history count.
- `GET /procedure-catalogue/:id/versions?page=&pageSize=` → `ProcedureTemplateVersionPage`, newest version first.
- `GET /procedure-catalogue/:id/history?page=&pageSize=` → paginated immutable lifecycle events, newest first.
- `POST /procedure-catalogue {fields,reason,requestId}` → `ProcedureTemplateMutation {detail,event,version}`, 201 on creation or 200 on exact replay. Creates an active unpublished template with version 1.
- `POST /procedure-catalogue/:id/versions {fields,reason,expectedRevision,requestId}` → mutation. Creates a new immutable draft; current publication remains usable. Identical latest content is rejected.
- `POST /procedure-catalogue/:id/publish {versionId,reviewed:true,reason,expectedRevision,requestId}` → mutation. Explicitly publishes the exact latest version. Archived templates and superseded versions are rejected. An author may review their own content; this is not an independent approval process.
- `POST /procedure-catalogue/:id/availability {active,reason,expectedRevision,requestId}` → mutation. Archives or reactivates without removing content or existing patient plans. Reactivation restores the retained publication.

Fields are `title`, `benefits`, `risks`, `alternatives`, `aftercare`, and descriptive `estimatedCost`. Title is required up to 300 characters; discussion fields are required up to 8,000; cost text may be empty and is limited to 300. Reasons are required up to 1,000 characters. Reads and commands reject extra query/body fields. UUIDs are canonicalized; commands bind the account, target, operation and complete normalized input. A changed request under the same UUID or stale revision returns 409. Replay returns the original event and its immutable version (null for availability changes), with current detail, before state/no-op checks. Source, evidence, receipt and audit commit together.

`revision` changes on every lifecycle event. `selectionRevision` changes on publication or availability changes, including archive/reactivate cycles, but not when saving a draft. Private catalogue changes do not notify patients or modify care-summary content.

### Procedure discussion and completion

- `POST /procedures {patientId,appointmentId?,title,indication,benefits,risks,alternatives,aftercare,estimatedCost?,requestId?,templateSelection?,reviewedForPatient?}` (linked clinician). Legacy manual requests without a UUID return `ProcedureRecord` with 201. UUID requests return `ProcedureCreateMutation {procedure,receipt}`, 201 initially or 200 on exact replay. Discussion fields are required, and estimated cost is descriptive text. An optional linked appointment must belong to the same patient and must not be cancelled or marked as a no-show. A procedure plan is immutable; create a new plan if its explanation changes.
- `POST /procedures/:id/agreements/record` accepts a `ProcedureDecisionCommand` from either portal. Send `{requestId,patientId,procedureId,recordedByRole,expectedLatestDecisionId,decision,method,note,patientDecisionConfirmed,reviewedConfirmed:true}`. Take the previous agreement ID from the last entry in the procedure history, or send `null` when the history is empty. A patient uses `portal` and sets `patientDecisionConfirmed:false`. A linked doctor or administrator uses `phone` or `in-person`, provides a discussion note and sets `patientDecisionConfirmed:true`.
- A new reviewed decision returns 201 with `{receipt:{requestId,actorId,patientId,procedureId,expectedLatestDecisionId,agreement}}`. An authorized exact retry returns 200 with the same receipt, including after a later decision, cancellation or completion. An intervening decision or terminal procedure rejects a new request with 409. A definitive refusal carries `code:'PROCEDURE_DECISION_NOT_RECORDED'`, the actor ID, normalized command and message. Retrying that command recovers its original refusal. To record a changed choice, read the current history, review the choice and submit a new UUID. Access failures and UUID conflicts do not prove the outcome of an earlier request.
- `POST /procedures/:id/agreements {decision,method,note?,patientDecisionConfirmed?}` → updated `ProcedureRecord` with `201`. Decision is `agreed | declined`. An owning patient uses `method:'portal'`. A linked clinician may record an `in-person` or `phone` decision only with a nonempty discussion note and `patientDecisionConfirmed:true`; clinicians cannot impersonate a portal acknowledgement. Each event retains the actual recording account, role, method and timestamp. This compatibility route appends an event for every accepted POST. Both current forms use the reviewed route above.
- `GET /procedures/:id/completion-context` returns `{procedure,doctorId,doctorName,revision,allowed,blockedReason}` to a linked doctor or administrator. The procedure includes the latest patient decision and effective visit. The performing clinician comes from the current account. The revision covers those reviewed details, the last visit association change, procedure state and current eligibility.
- `POST /procedures/:id/completions` accepts `{requestId,patientId,procedureId,doctorId,recordedByRole,expectedRevision,expectedDecisionId,outcome,aftercare,reviewedConfirmed:true}`. Use the latest agreement ID and the revision from the context. A new completion returns 201 with `{receipt:{requestId,actorId,patientId,procedureId,expectedRevision,decisionId,completion}}`. An authorized exact retry returns the same receipt with 200, including the recorded clinician, server timestamp and visit snapshot. The shared clinical record contains the completion.
- A stale review or ineligible procedure returns 409. A definitive refusal includes `code:'PROCEDURE_COMPLETION_NOT_RECORDED'`, actor ID, normalized command, message and `observed:{decisionId,status}`. These last two values describe the latest decision and procedure state at the time of refusal. An exact retry of that command recovers the refusal even if the procedure becomes eligible later. After a refusal, review fresh context before sending a new UUID. Access errors, changed payloads under a used UUID and unexpected replies do not establish the outcome of an earlier request.
- `POST /procedures/:id/complete {outcome,aftercare}` → updated `ProcedureRecord` (linked clinician). The latest recorded decision must be `agreed`. Completion records the performing doctor and server timestamp and requires outcome and aftercare. The effective appointment is resolved inside the transaction; it must exist, not be cancelled/no-show, and have started. New completion records include its safe `appointment` snapshot, or `null` when unlinked; legacy completions are not backfilled.
- `POST /procedures/:id/cancel {reason}` → updated `ProcedureRecord` (linked clinician).

Template selection is `{templateId,versionId,expectedSelectionRevision}` and requires a request UUID and `reviewedForPatient:true`. All final fields remain explicit, including the patient-specific indication. The server checks the active current publication and selection token in the plan transaction, then derives safe immutable `templateSource` attribution and changed-field names. Own-patient records and summaries include that attribution, never internal catalogue reasons, tokens, receipts or unpublished content. Later publication/archive does not change the saved plan. Exact actor-bound retries return the original receipt and current view of the same plan before later source/appointment eligibility checks; changed payload or actor under the UUID is rejected. Receipt, plan, audit and patient notification commit together.

A procedure starts as `planned`; `completed` and `cancelled` are terminal. Patient decisions can change while planned, and all earlier decisions remain visible. Agreement checks and completion/cancellation run transactionally. Completing or cancelling a procedure neither changes its appointment nor creates a billing charge. No separate procedure time slot is reserved.

### Scheduling existing procedure plans

These endpoints allow administrator, doctor and receptionist accounts. Patients are denied private scheduling reads and writes. Operational projections omit clinical discussion, agreement notes, outcomes, appointment reasons, fees and patient contacts.

- `GET /procedure-scheduling?search=&status=&booking=&page=&pageSize=` → `ProcedureSchedulePage`. Defaults: empty search, `status:planned`, `booking:all`, page 1, page size 25. Status is `planned|completed|cancelled|all`; booking is `unlinked|linked|attention|all`. Literal search matches patient name or procedure title, up to 300 characters. Page sizes are 10/25/50; out-of-range pages clamp. Rows sort by original creation date and ID descending. Filtering, counting and pagination happen in SQLite before row JSON decoding, in one coherent transaction.
- `GET /procedures/:id/scheduling` → `ProcedureScheduleContext {procedure,revision,history}`. The row contains original and effective appointment IDs, a safe current appointment snapshot, operational status, `canChange` and `blockedReason`. Immutable link events are newest first. The revision covers procedure identity/status, original/effective links, the current visit snapshot and latest link event.
- `GET /procedures/:id/scheduling/candidates?from=&to=&page=&pageSize=` → `ProcedureCandidatePage`. Returns same-patient future scheduled visits, excluding the current effective visit, with a revision of each safe snapshot. Dates default to today through 180 days ahead; explicit ranges must stay within that horizon. Page sizes are 10/25/50, with stable date/time/ID ordering and clamped pages.
- `POST /procedures/:id/scheduling {appointmentId,expectedAppointmentRevision,expectedRevision,requestId,reason,removeConfirmed?}` → `ProcedureScheduleMutation {context,event}` with 200. Attaching/replacing requires a target ID and its revision. Removal requires null ID/revision and `removeConfirmed:true`; that flag is rejected for a nonnull target. Reasons are trimmed, required and limited to 1,000 characters. Extra/duplicate query fields and extra command fields are rejected.

Only planned procedures can change links. A current missing/cancelled/no-show visit, future scheduled visit, or no link is eligible; a visit already checked in, in consultation, completed or past its scheduled start is read-only. Targets must be future scheduled visits for the same patient. Different clinicians/modes and multiple plans sharing a visit remain allowed; the link does not establish clinical suitability or sufficient combined duration. Source/target changes return 409; unchanged associations return 400.

The original `ProcedureRecord.appointmentId` remains immutable. Hydrated workflows and summaries add `effectiveAppointmentId` and `scheduledAppointment`; an explicit removed link stays null rather than falling back to the original. Patient projections contain no scheduling events, reasons, actor IDs, revisions or retry tokens. New completion snapshots are separate from the current linked visit, which can later reflect ordinary appointment changes.

Canonical lowercase UUIDs bind actor, procedure and normalized command. Exact replay occurs after authorization but before source/state/eligibility checks, returning the original event plus current context. Events and receipts reject updates/deletion. Link evidence, receipt, audit and generic patient activity commit atomically. Link changes do not edit appointments, resource reservations, original plans, agreements, completion evidence or invoice sources. Booking a new visit is a separate existing workflow; it does not automatically attach a plan.

These records capture a clinician's explanation and a reported patient decision. They are not an electronic-signature workflow or a certification of legally sufficient informed consent. There is no automatic treatment recommendation, drug-warning validation, laboratory connection or interpretation of report contents. Long clinical text fields have an 8,000-character limit.

## Billing and approved knowledge

- `GET /invoices` → `Invoice[]` (staff or owning patient).
- `GET /procedure-billing?patientId=` → `ProcedureBillingItem[]` (staff; patient accounts denied). Returns only `id`, `patientId`, `patientName`, `title`, `estimatedCost`, `status`, nullable `invoiceId` and `invoiceNumber`. Clinical indication, risks, benefits, alternatives, aftercare, decisions and outcomes are omitted; reception cannot fetch the full clinical record.
- `POST /invoices/issue {requestId,patientId,items,procedureId?,reviewedConfirmed:true}` → `{receipt:{requestId,actorId,patientId,invoice}}`. Staff review the ordered charge lines before issuing. A first save returns 201. An exact retry by the issuer returns 200 with the originally issued invoice, including the original patient and procedure names, unpaid status and zero recorded payments. Read the invoice detail for current charges and balances.
- `POST /invoices {patientId,items:[{description,quantity,unitAmountPaise}],requestId?,procedureId?}` → `Invoice` with `201` (staff). Money uses integer paise. With a new UUID request ID, an exact retry by the same staff account returns the current invoice with 200. The legacy and reviewed routes share UUIDs. Changing issuer, patient, procedure or line items under that ID returns 409. Quantities are integers from 1–1,000; unit amounts are positive integers; total invoice value is capped at 1,000,000,000 paise. Totals and initial unpaid status are server-derived.
- `GET /invoices/:id` → `InvoiceDetail {invoice,payments,invoiceId,issuedCharges,corrections,reversals,refunds,refundVoids,revision}` (staff or owning patient).
- `POST /invoices/:id/payments/record {requestId,patientId,expectedRevision,amountPaise,method,reference,receivedExternallyConfirmed:true}` records money already received outside the app. Supply the revision from the reviewed invoice detail and a positive integer amount up to 1,000,000,000 paise. Methods are `cash`, `card`, `upi` and `bank`. The reference can be an empty string. A new save returns 201 with `{receipt:{requestId,actorId,invoiceId,patientId,expectedRevision,invoiceNumber,totalPaise,beforePaidPaise,afterPaidPaise,payment:{id,invoiceId,createdAt,amountPaise,method,reference}}}`. An authorized exact retry by the recorder returns 200 with the same receipt, even after a correction, reversal, refund or another payment.
- `POST /invoices/:id/payments {amountPaise,method,reference?,requestId}` → `InvoiceDetail` (staff). UUID request ID is required. Methods are `cash | card | upi | bank`. An exact retry of a new legacy request by the same staff account returns current detail; changed request content and overpayment are rejected. This records a payment received elsewhere; it does not charge a payment provider.
- `POST /invoices/:id/corrections {items,reason,expectedRevision,requestId,removeAllChargesConfirmed?}` → `InvoiceDetail` (administrator). The replacement items use the same quantity/paise bounds as invoice creation, with 0–100 lines. An empty list requires `removeAllChargesConfirmed:true`; this flag must be omitted for nonempty items. The total cannot fall below net recorded payments. Unchanged items return `400`. Removing all charges with zero net paid produces `status:'no-charge'`; a later correction can add charges to the same invoice.
- `POST /invoices/:id/payments/:paymentId/reverse {reason,entryErrorConfirmed:true,expectedRevision,requestId}` → `InvoiceDetail` (administrator). Reverses one entire erroneous payment entry on that invoice. The original payment stays immutable; a different request to reverse an already reversed entry or any payment with a nonvoided refund returns `409`. This corrects a record and does not refund money.
- `POST /invoices/:id/payments/:paymentId/refunds {amountPaise,method,reference?,reason,refundedExternallyConfirmed:true,expectedRevision,requestId}` → `PaymentRefundMutation {detail,refund,receipt}` with `201` new / `200` exact replay (administrator). Positive integer paise up to 1,000,000,000, methods `cash | card | upi | bank`, trimmed reference up to 200 characters and required for noncash methods, trimmed reason 1–1,000 characters, current 64-hex invoice revision and UUID command ID. Unknown body/query fields are rejected. The payment must belong to this invoice, be nonreversed, and have sufficient unrefunded balance. Refunds reduce net paid and update status; charges remain unchanged.
- `POST /invoices/:id/refunds/:refundId/void {reason,entryErrorConfirmed:true,expectedRevision,requestId}` → `PaymentRefundVoidMutation {detail,void,receipt}` with `201` new / `200` exact replay (administrator). The entire mistaken refund must belong to this invoice, be nonvoided and have a nonreversed source payment. Its amount is derived from the original refund. Restored net paid must not exceed current charges; otherwise `409` requires a separate review/correction. The strict body requires a trimmed 1–1,000-character reason, current revision, UUID command and explicit entry-error confirmation; unknown query fields are rejected.
- `GET /knowledge` → published `KnowledgeArticle[]` (public).
- `GET /knowledge/manage` → all `KnowledgeArticle[]` (clinician).
- `POST /knowledge {title,category,body}` → draft `KnowledgeArticle` (clinician).
- `PATCH /knowledge/:id {title?,category?,body?,status?}` → `KnowledgeArticle` (clinician). Edited content becomes draft unless explicitly reapproved with `status:'published'`.

Both issuance routes recheck the session, staff role and patient inside the write transaction. A reviewed command for a missing or wrong-patient procedure returns 400. A cancelled or already-invoiced procedure returns 409. These procedure rejections include `{code:'INVOICE_NOT_ISSUED',actorId,command,message}` and remain final for that request ID. An exact match permits fresh review. A bare error, including an authorization or UUID conflict, provides no confirmation of the original outcome. An invoice UUID recorded before v1.44 has no verified issuer and returns 409 on either issuance route. Staff can look up that invoice in Billing.

Both payment writers check the current staff session and accessible invoice inside the write transaction. The reviewed route stores a final 409 for an outdated revision or an amount that exceeds the outstanding balance. Its body is `{code:'PAYMENT_NOT_RECORDED',actorId,invoiceId,command,message}`. Matching the full command lets the recorder refresh the invoice and review a new attempt. Authorization, mismatched patient and request-ID collisions do not carry this marker. Once the server stores an outcome, reusing that request ID with a different staff account, invoice, payload or payment endpoint returns an unmarked 409. An ID found on a pre-v1.45 payment has no verified recorder and returns 409 on retry. The original payment and current invoice detail remain readable.

The reviewed request ID is private to the recording workflow. In the existing `InvoiceDetail.payments` representation, `requestId` on a newly reviewed payment is its payment-record ID. Legacy rows retain their existing values.

Billing corrections require a current 64-hex revision, UUID request ID and trimmed 1–1,000 character reason. Reasons, attributed histories and before/after values are explicitly shared with the patient. Safe histories omit internal account/request IDs. A correction preserves invoice number, issue date, patient-name snapshot and procedure linkage. `issuedCharges` retains original line items and total; `invoice` contains current corrected charges and net paid. `payments` retains all originals, while `reversals` identifies excluded entries. Invoice-creation retries compare the original issued items even after correction; replaying a reversed original payment request never reinstates it.

Correction commands bind the request ID to the actor, operation, invoice, payment and normalized payload, excluding the expected revision. Exact replay returns the current detail before stale checks; mismatched reuse returns `409`. New changes require review after concurrent payment/correction/reversal updates. Source history, current balance, request receipt, audit and generic patient activity commit atomically. Corrections remain readable to all authorized invoice readers, but only administrators can write them.

Refund commands share the correction-command namespace but bind the reviewed revision as well as actor/action/invoice/payment and normalized payload. Current account/session/CSRF/MFA authorization is revalidated under the write lock, including replay. The immutable refund, current invoice balance, command receipt, audit and generic patient notice commit together. An exact retry returns the original refund and receipt alongside later-current invoice detail; it never records another refund. A stale revision, exhausted amount or conflicting command ID returns `409`.

`PaymentRefund` exposes `id,invoiceId,paymentId,amountPaise,method,reference,reason,refundedExternallyConfirmed,beforePaidPaise,afterPaidPaise,createdByName,createdAt`. Safe invoice history and patient summaries omit private command/account IDs. Only the mutation receipt includes `requestId,actorId,invoiceId,paymentId,expectedRevision,refundId`. Original refunds cannot be updated or deleted; an attributed void is a separate immutable record. Recording confirms a manual entry about money returned elsewhere; it initiates no transfer.

`refundVoids` contains safe `PaymentRefundVoid` entries: `id,invoiceId,refundId,paymentId,amountPaise,beforePaidPaise,afterPaidPaise,entryErrorConfirmed,reason,createdByName,createdAt`. The private mutation receipt includes `requestId,actorId,invoiceId,refundId,expectedRevision,voidId`. Source refund content remains unchanged. A refund can have one void; there is no edit, deletion or undo route. Voided entries are excluded from current refund totals, per-payment caps and the payment-reversal guard. Reversal of an original payment still requires a separate confirmed command.

Void commands share the actor/action/source/payload-bound billing namespace and include the reviewed revision and refund ID. Current authorization is checked under the lock before replay; an exact retry returns the original void/receipt with later-current invoice detail, even after a replacement refund or original payment reversal. Current balance, immutable void, receipt, audit and generic patient notice commit atomically. Care summaries include safe void history, while older saved copies without this additive field remain unchanged and readable. No receipt or transfer is created by a void.

A procedure can have one linked invoice. It must belong to the invoice patient and must not be cancelled when linking a new invoice. An existing link returns `409` for another creation request; the UI opens its existing invoice. Matching retries reuse the original invoice even if the procedure was subsequently cancelled. Linked invoices include `procedureId` and the original `procedureTitle` snapshot. Linking is immutable and commits with invoice creation, sequence allocation, audit and patient activity.

Procedure estimates never populate a charge automatically: staff enter the agreed line items and amounts explicitly. Planning/completing a procedure does not create an invoice; creating an invoice does not record a payment. Cancelling a procedure does not change an existing charge or create a refund. Actual payment collection and refund transfers, tax calculation and external reconciliation require separate clinic processes.

Administrator insights retain `collectionsPaise` for nonreversed received-payment entries. Totals additionally expose `refundCount,refundsPaise,netCollectionsPaise`; daily rows include `refundsPaise,netCollectionsPaise`, and `refundsByMethod` contains counts/amounts by return method. Refund inclusion uses its original `createdAt` in Asia/Kolkata, independent of payment/issue dates, and excludes currently voided erroneous entries. The void date creates no new cash-flow cohort. Net collections can be negative. JSON and aggregate CSV use the same calculation and exclude refund free text and identities.

Mutation responses contain `{detail,event,version}`. `event` and `version` identify the exact original accepted command; `detail` is current and may include later changes. Request keys bind actor, operation, target, revision and normalized payload. After checking current permission, exact replay is resolved before stale-state checks. Legacy `/knowledge` and `/knowledge/manage` arrays remain compatible. Legacy creation still ignores extra status fields and creates a draft; PATCH retains partial-field and explicit-status behavior. ## Consumable inventory

All inventory routes allow staff reads (`admin`, `doctor`, `receptionist`) and administrator mutations. Patients and temporary-password sessions cannot access inventory. No operation creates a charge, expense, prescription or patient association.

- `GET /inventory/items?search=&active=true|false|all&stock=low|expired|expiring-soon` → `InventoryItem[]`; active items by default. Search matches the catalogue; stock filters select items with the corresponding condition.
- `GET /inventory/items/:id` → `InventoryDetail {item,lots,itemChanges}`. Includes immutable catalogue snapshots with author, reason and date, newest first.
- `GET /inventory/items/:id/movements?limit=&cursor=` → `InventoryLedger {items,nextCursor}`; newest first, default 50 and maximum 100. Cursors are opaque movement IDs scoped to the item.
- `POST /inventory/items` accepts `{sku,name,category,unit,reorderLevel,requestId}` → `201 InventoryDetail`; an exact retry returns `200`.
- `PATCH /inventory/items/:id` accepts `{name?,category?,reorderLevel?,active?,reason,expectedRevision,requestId}` → `InventoryDetail`. SKU and unit are immutable. Edits retain an attributed catalogue snapshot; archive/reactivation preserve all stock history.
- `POST /inventory/items/:id/receipts` accepts `{quantity,lotCode?,expiryDate,reason,reference?,expectedRevision,requestId}` → `201 InventoryMutation {detail,movement}`. `expiryDate` is an exact calendar date or `null`. Every receipt creates its own immutable lot, even when supplier lot labels repeat.
- `POST /inventory/lots/:id/use` accepts `{quantity,reason,reference?,expectedRevision,requestId}` → `InventoryMutation`. The item must be active, the lot must not be expired, and sufficient stock must remain.
- `POST /inventory/lots/:id/adjust` accepts `{countedQuantity,reason,reference?,expectedRevision,requestId}` → `InventoryMutation`. It records the observed whole-unit balance, deriving the signed adjustment from the current lot balance. A zero adjustment still records the count. Inactive and expired lots can be reconciled.

Categories are `dressings`, `protective-equipment`, `instruments`, `cleaning`, `office`, `other`. Units are `piece`, `pair`, `pack`, `box`, `bottle`; they count whole units without conversions. SKU is normalized uppercase, 1–50 characters: a leading letter/digit followed by letters, digits, periods, underscores or hyphens. Names are 1–150 characters; lot codes up to 100; reasons 1–1000; references up to 200. Receipt/use quantity is an integer from 1 to 1,000,000. Counts and lot/item balances are bounded from 0 to 1,000,000,000; reorder thresholds from 0 to 1,000,000.

`InventoryItem` exposes on-hand, unexpired, expired and expiring-soon quantities, a low-stock flag and a revision. A lot is expired when its recorded expiry date is before today's Asia/Kolkata date. Expiring soon covers today through 30 days ahead, inclusive. Unknown expiry is explicitly `null`; it contributes to unexpired quantity without claiming suitability for use. Low stock means an active item's unexpired balance is at or below its reorder threshold. Already-expired receipts may document existing physical stock but cannot subsequently be used.

Stock balances derive from immutable movements; `balanceAfter` is the recorded balance of that lot after the event, not a current balance or item total. Catalogue originals, changes, lot metadata and movements are retained. Revisions include catalogue/stock changes and the clinic date, so a day rollover requires refresh before a new stock operation. Global request UUIDs are bound to the actor, operation and normalized business payload. Exact retries resolve before revision checks and return the original event with current detail; reusing a key for different input or an account conflicts. Revision/balance checks, source events, request receipts and audit entries commit in one transaction. Failed audits do not leave partial stock changes.

Active reservations ending after now cannot overlap new maintenance.

All writes require a canonical UUID bound to actor, operation, target and normalized intent. Exact replay precedes revision and no-op checks; reasons require 1–1000 characters. Revisions cover relevant catalogue, maintenance and reservation changes. Immutable history, replay receipts, current claims and audit records commit together. ## Paginated record search

The additive `/search/*` endpoints return `SearchPage<T> {items,page,pageSize,total,totalPages}`. `page` defaults to 1 and accepts 1–1,000,000; `pageSize` defaults to 25 and accepts 1–100. The server clamps the requested page to the last available page; an empty result has page 1 and totalPages 1. COUNT and limited SELECT use one SQLite read transaction. Separate requests show current data, with no guarantee of stable row positions after concurrent additions or edits.

- `GET /search/patients?q=&page=&pageSize=` is staff-only. Returns demographic `PatientDirectoryItem` rows (id, name, email, phone, date of birth, gender, registration timestamp), newest registration first with descending ID as a deterministic tie-breaker. Search matches name, email, phone or patient ID. Allergy fields, clinical status and private correction history neither appear nor influence matches/counts.
- `GET /search/appointments?q=&from=&to=&doctorId=&patientId=&status=&mode=&page=&pageSize=` is staff-only. Dates filter the scheduled clinic date and may be one-sided. Status accepts any appointment status or `waiting` for scheduled/checked-in. Mode is `in-person|online`. Search matches the saved patient-name snapshot or current patient name/contact/ID; returned `Appointment` values retain original snapshots. Sort is date/time/ID ascending.
- `GET /search/audit?q=&actor=&action=&entityType=&entityId=&from=&to=&page=&pageSize=` is administrator-only. General text searches visible audit fields and entry ID. Actor/action are literal substring filters; record type/ID are exact. Date bounds include the whole selected IST days, compared against the stored UTC timestamps. Sort is timestamp/ID descending. There is no 500-entry ceiling and reads do not generate recursive audit entries.

Text searches are trimmed and capped at 200 characters; identifiers at 300. Real `YYYY-MM-DD` dates are required, ordered when both bounds are supplied. Unknown, duplicate, malformed and oversized parameters return 400. Patients and temporary-password sessions cannot use these staff endpoints. Every result uses `Cache-Control: no-store`. SQL parameters and `instr` treat percent signs, underscores, quotes and backslashes literally. Built-in SQLite lowercase matching folds ASCII letters; it is not Unicode case-folding or fuzzy search.

Filtering, counting, sorting and limiting execute in SQLite, and only returned rows are decoded in application memory. Date/doctor/patient/status/mode and audit date/record indexes support common filters; arbitrary substring matches may still scan candidates. No response size or constant-time full-text search guarantee is implied for older compatibility APIs: `/patients` and `/appointments` still return arrays. `/audit` keeps its original latest 500 array contract but now applies that limit in SQL.

## Staff attendance

Attendance belongs to a staff account, not a doctor profile or patient. Patients and temporary-password sessions cannot access these endpoints. Staff can read only their own entries; administrators can inspect and correct all staff, including inactive accounts. Staff identities contain only ID, name, role and active status. Reads use `Cache-Control: no-store`.

- `GET /attendance/me` → `AttendanceContext {staff,revision,openShift,serverNow,timezone}` for the current account.
- `GET /attendance/staff` and `GET /attendance/staff/:id/context` are administrator-only; the latter supplies the target account revision for recording missed attendance.
- `POST /attendance/clock-in {requestId,expectedRevision}` starts the current account's entry using server time. New entries return 201; exact retries return 200.
- `POST /attendance/shifts/:id/clock-out {requestId,expectedRevision}` ends the caller's own open entry using server time; its expected revision comes from `/attendance/me`.
- `POST /attendance/shifts {userId,startedAt,endedAt,reason,requestId,expectedRevision}` records a missed closed interval; administrator-only, using the target account-context revision.
- `GET /attendance/shifts/:id` → `AttendanceDetail {shift,events}` for the owner or an administrator. Missing and forbidden entry IDs return 404 to other staff.
- `POST /attendance/shifts/:id/corrections {startedAt,endedAt,reason,requestId,expectedRevision}` records an administrator correction using the shift revision. It can close an open entry or change a closed interval, but cannot reopen or change the staff identity.
- `POST /attendance/shifts/:id/void {reason,requestId,expectedRevision}` marks an erroneous entry void using the shift revision. Voiding is terminal, preserves history and releases an open interval.

All mutations return `AttendanceMutation {shift,event}`: the current effective shift and the immutable receipt for that exact command. Events preserve the request UUID, expected revision, before/after times, reason and actor identity. Canonical lowercase UUIDs are bound to actor, operation, target and normalized payload. Exact retries precede current-state/revision checks after authorization; changed commands return 409. Account revisions change with any attendance event for that account; shift revisions change with that entry's events. Uncertain client responses must retain the same payload and UUID until confirmed.

Timestamp inputs are real canonical UTC ISO strings with milliseconds. Times cannot be future, the end cannot precede the start, and a completed interval cannot exceed 36 hours. A zero-second interval is allowed for rapid clocking. Staff can have one open entry; nonvoid intervals cannot overlap, while adjacent intervals are allowed. An open entry older than 36 hours requires administrator correction or voiding. Logout, suspension and password changes never fabricate an end time. Reasons are required for administrator entries and changes, and are visible to the affected staff member.

`GET /attendance?from=&to=&userId=&status=&page=&pageSize=` returns `AttendanceReport`, extending `SearchPage<AttendanceShift>` with the applied filters, timezone, generation time, whole-result revision and totals (`closedShiftCount`, `recordedSeconds`, `openShiftCount`, `voidedShiftCount`). Dates are inclusive IST **start dates**, ordered and at most 366 days. Completed intervals contribute their entire floored elapsed seconds to their effective start-date cohort; open/voided entries contribute no time. Administrators may omit `userId` for all staff; other staff are restricted to their own ID, with another ID rejected as 403. Status is `all|open|closed|voided`. Pages default to 1 and 25 rows, with maxima 1,000,000 and 100; requests clamp to the last page. Sort is effective start timestamp descending, then ID descending. Counts, totals, revisions and page rows share one database snapshot.

`GET /attendance/export.csv` is administrator-only and takes the same date/user/status filters plus `expectedRevision`, without page parameters. It exports effective attendance fields and status, omitting correction reasons and account contact/clinical data. The revision covers the full filtered report, independent of pagination. Changed reports return 409; more than 10,000 matches return 422 rather than truncating. Confirmed responses use CSV content type, attachment disposition and `X-Attendance-Revision`; spreadsheet formula prefixes are escaped. No attendance operation changes payroll, expenses, patient activity or appointment availability.

Every signed-in role can use `/account`; temporary-password sessions are directed there before entering their workspace.

Patient waitlist links use `/my-care?waitlist=id`; booking from a request uses `/book?waitlist=id` with a fixed clinician/mode and constrained date window. `/my-care?plan=id` reveals the selected active or completed plan. Record sections accept `?tab=careplans`, `workflows`, `images` or `visits`. Procedure billing uses `/clinic/billing?procedure=id`; invoice links use `?invoice=id` on the staff or patient invoice route.

Shared client helpers in `src/lib.tsx` include `api<T>()`, `useSession()`, `useResource<T>()`, `useToast()`, `today()`, `formatDate()` and `money()`. Shared accessible controls live in `src/components/ui.tsx`; page-specific styles supplement `src/styles.css`.

Investigation queue selection uses `/clinic/investigations?investigation=id`. Exact clinic record links use `/clinic/patients/:id?tab=workup&investigation=id&result=id`; the requested record/result is revealed and focused, including cancelled history, with unavailable targets explicitly identified. Changing record tabs clears these selections.

Resource diary selection uses `/clinic/resources?date=YYYY-MM-DD&resource=id`. Appointment allocation/history links use `/clinic/appointments?date=YYYY-MM-DD&resources=id`, including terminal visits.

The patient directory uses `?search=&page=`; appointment views use `?date=&allDates=1&doctorId=&status=&mode=&search=&page=`. Audit filters mirror its search API query fields. Filter changes reset pagination; confirmed server page clamping replaces the URL. Browser Back/Forward restores the applied view.
